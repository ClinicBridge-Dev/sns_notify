# Meta Business Suite → Slack 알림 연동 검토

> 구현 기획서(meta-inbox-extension-implementation-spec.md)에서 서버 경유가 아닌 Slack 직접 전송으로 확정했다. 이 문서는 검토 배경으로만 본다.

작성일: 2026-11-12
재검토일: 2026-11-12
상태: 현재 작업 트리의 코드와 변경된 운영 환경을 대조한 설계 문서. 이번 재검토에서는 문서만 수정하며, 구현·설정 변경·Slack 전송은 수행하지 않음.

## 0. 플랫폼 변경에 따른 판단

**WhatsApp과 Instagram 모두 Meta Business Suite에서 운영한다면, 수집 경로를 Business Suite 목록 감지 확장 프로그램으로 통합하고 기존 로컬 FastAPI·SQLite·Slack 전송기를 재사용하는 방향이 적절하다.** 다만 기존 확장에 도메인만 추가해서는 동작하지 않는다. 목록 구조, 계정·대화 식별, 신규 판정, 상태 감시를 함께 바꿔야 한다.

| 구분 | 현재 코드 | 변경 후 설계 |
| --- | --- | --- |
| WhatsApp 감지 | macOS WhatsApp 앱의 AX 대화 목록 | Business Suite WhatsApp 목록 DOM |
| Instagram 감지 | instagram.com의 Primary·General·요청 목록 DOM | Business Suite Instagram 목록 DOM |
| 공통 전송 | 로컬 FastAPI → SQLite `notices` → Slack Bot API | 기존 경로 재사용, Meta 공통 ingest 추가 |
| 알림 단위 | 채널별 미리보기·안 읽음 변화 | 관찰된 대화 변화. 메시지별 정확한 건수로 표시하지 않음 |
| 계정 연결 | WhatsApp 설정 + Instagram 사용자명별 연결 | 업무 자산·채널별 계정 키 → 고객사/Slack 채널 |
| 감시 화면 | WhatsApp 앱 + Instagram 목록별 창 | 먼저 Business Suite 채널별 목록 2개를 검증. 필요한 추가 필터는 실측 후 결정 |

운영 화면이 하나가 되어도 두 채널의 식별자와 수신 상태를 합치지는 않는다. 같은 이름의 Instagram 고객과 WhatsApp 고객을 자동으로 동일인으로 묶지 않는다. Business Suite 사용 자체가 공식 API 권한 확보를 의미하지도 않는다.

## 1. 목적과 전제

Instagram과 WhatsApp의 새 문의를 놓치지 않도록 Slack으로 알린다. 전체 대화 수집이나 자동 답장은 목적이 아니다.

- 사용자는 현재 Meta Business Suite에서 WhatsApp과 Instagram을 모두 운영한다.
- 공식 Meta API는 현재 사용할 수 없다는 기존 문서의 전제를 유지한다. 플랫폼 변경만으로 이 제약이 해소됐다고 가정하지 않는다.
- 사용자는 Meta Business Suite 탭과 로그인 상태를 유지할 수 있다.
- 가능하면 발신자 표시 이름/아이디와 짧은 메시지 미리보기를 함께 전달한다.
- 계정 제한 위험을 낮추는 것이 정보 수집량보다 우선이다.
- 기존 구현은 이번 재검토에서 확인했다. WhatsApp AX 목록 감지와 Instagram DOM 감지를 공통 알림 저장·전송 코드에 연결하는 구조다.

## 2. 현재 확인한 플랫폼 구조

### 사용자에게 보이는 구조

Instagram·WhatsApp 메시지 → Meta Business Suite 통합 수신함 → 채널별 대화 목록과 선택한 대화의 본문

기존 문서에는 Instagram·WhatsApp 수신함 항목과 WhatsApp 목록의 이름/전화번호·미리보기를 확인했다고 기록되어 있다. 이번 재검토에서는 사용자 설명과 그 기록을 운영 전제로 사용했다. 로그인된 실제 페이지를 새로 관찰하거나 DOM을 추출하지는 않았다.

이번 설계는 선택된 대화의 본문·연락처가 아니라 대화 목록의 최소 정보만 관찰하는 것을 대상으로 한다. 문서에는 실제 고객 정보나 메시지를 포함하지 않았다.

### 아직 확인하지 않은 사항

- Instagram 목록에서 실제로 제공되는 발신자 식별 정보와 미리보기 형식
- 채널별 탭을 동시에 열었을 때 양쪽 목록의 실시간 갱신 여부
- 백그라운드 탭, 긴 유휴 시간, 절전 이후의 갱신 동작
- DOM에 안정적인 대화 ID나 메시지 ID가 노출되는지
- 목록 밖 대화의 갱신과 가상화 여부
- Meta가 두 채널의 OS 알림을 어떤 조건에서 내보내는지
- 현재 WhatsApp 번호의 API 연결 유형

현재 화면을 확인했다는 사실만으로 위 동작이나 무누락 수신을 보장할 수 없다.

### 현재 코드에서 확인한 차이

## 3. 가능한 방법

### A. 공식 API / Webhook

구조: Meta 공식 Webhook → 서버 → Slack

새 메시지 이벤트를 공식적으로 받는 전환 후보다. 기존 문서에 Instagram 및 WhatsApp의 수신 메시지 Webhook 자료가 기재되어 있다. 이번 재조회에서는 Meta 문서가 HTTP 429를 반환해 최신 세부 조건을 재확인하지 못했다.

장점: 공식 연동 경로이며 브라우저 화면 변경에 덜 민감하다.
조건: 계정 연결, 권한 부여, 운영 범위에 따른 앱 검토 및 온보딩 등이 필요하다.
판단: 현재 사용할 수 없으므로 이번 구현 범위에서 제외한다. 향후 가능해질 때 전환 후보로 남긴다.

Business Suite 통합 수신함을 쓴다는 이유만으로 하나의 공통 Webhook을 바로 연결할 수 있다고 설계하지 않는다. API 전환 시에는 채널별 권한·자산 연결을 확인하고, 특히 WhatsApp 번호의 Business App/Cloud API 연결 유형과 기존 Business Suite 수신함 유지 여부를 별도로 검증한다.

### B. OS 알림 감지

구조: Meta 데스크톱 알림 → macOS 로컬 앱 → 필터·중복 제거 → Slack

손쉬운 사용 권한 등을 가진 로컬 프로그램이 OS에 실제 표시되는 알림을 관찰하는 접근이다. 현재 저장소의 WhatsApp 구현은 OS 알림이 아니라 공식 데스크톱 앱의 대화 목록을 읽는다. 따라서 기존 AX 코드를 그대로 OS 알림 보조 경로로 간주할 수 없다.

장점: Meta 페이지의 대화를 자동으로 열거나 추가 조회할 필요가 없다.
한계: 알림 미발생, 알림 묶음, 미리보기 숨김, OS 변경, 절전 등에 영향을 받는다. 알림에 없던 아이디나 본문을 보충할 수 없다.

Chrome 확장 프로그램의 notifications API는 해당 앱·확장 프로그램이 만든 알림을 관리한다. 다른 웹사이트가 만든 OS 알림을 모두 읽는 범용 API가 아니다. 따라서 확장 프로그램의 알림 권한만으로 기존 OS 알림 수집을 그대로 대체할 수는 없다.

판단: 이미 검증된 기존 구현이 있다면 보조 수단으로 검토한다. 단독 사용으로 무누락을 보장하지 않는다.

### C. 페이지 대화 목록 감지 확장 프로그램

구조: Meta 수신함 DOM → 확장 프로그램 → 중계 서버 → Slack

페이지에 이미 표시된 대화 목록의 변화를 관찰한다. 예를 들어 MutationObserver로 변경을 감지하고, 변경된 목록 상태를 비교한다. 페이지 내부 통신을 가로채거나 비공개 API를 호출하는 방식은 사용하지 않는다.

장점: OS 알림 표시 여부와 별개로 목록 변화를 감지할 수 있다. 목록에 제공되는 이름·미리보기를 사용할 수 있다.
한계: DOM 변경, 목록 가상화, 탭 정지, 세션 만료, 미리보기 덮어쓰기, 식별자 부족의 영향을 받는다. 표시되지 않은 데이터는 수집하지 못한다.
정책: 화면에 보이는 정보만 수집해도 Meta의 자동 수집 정책 적용 가능성이 남는다. 수집량이 적다는 이유로 승인된 방식이나 제재 위험이 없는 방식이 되지는 않는다.

판단: 현재 조건에서 기술 검증할 후보. 정책 위험을 수용할 수 있다는 전제하에 소규모 검증부터 진행한다.

### D. 자동 대화 열기 / 내부 API 호출

대화를 자동 클릭하거나 스크롤하며 본문을 수집하거나, 로그인 쿠키로 내부 API를 반복 호출하는 방식이다.

판단: 이번 목적에 불필요하며 정책·보안·유지보수 위험을 높이므로 제외한다. 계정 쿠키, 세션 토큰, 개인 인증정보를 수집하거나 서버에 전달하지 않는다.

## 4. 권장 후보 구조

```text
Meta Business Suite
  ├─ Instagram 목록용 탭/창 ─ Instagram 목록 파서 ┐
  └─ WhatsApp 목록용 탭/창 ── WhatsApp 목록 파서 ┘
      → 공통 스냅샷 + 확장 프로그램 영속 대기열
      → 기존 로컬 FastAPI의 /api/ingest/meta (신설 제안)
      → 대화 변화 판정 + SQLite notices
      → 기존 NoticeSender + SlackSdkPoster
      → 계정별로 연결한 Slack 채널
```

이는 제안 구조이며, 두 전용 탭이 실제로 동시에 갱신되는지는 테스트해야 한다. 각 탭에 business.facebook.com의 동일한 DOM 구조가 나타난다고 가정하지 않는다.

### 감시 화면의 범위

- 처음에는 채널을 명확히 구분할 수 있는 Instagram·WhatsApp 목록을 각각 검증한다. 두 탭이 선택 자산/필터 상태를 공유해 서로 바뀌는지도 확인한다.
- ‘전체’ 수신함 한 탭으로 줄이는 것은 각 행의 채널·계정을 식별하고 양쪽 채널의 갱신 및 누락 범위를 검증한 뒤에만 고려한다. 전체 목록에는 범위 밖 메시지나 댓글이 섞일 가능성도 확인한다.
- ‘미읽음’, ‘내게 배정’, 검색 결과 등 제한된 필터는 전체 감시 기준으로 삼지 않는다. 다른 담당자가 읽거나 배정을 바꾸는 순간 목록에서 사라질 수 있다.
- Instagram의 Primary·General·요청 구조가 Business Suite에도 그대로 있다고 가정하지 않는다. 요청·스팸·보관/완료 대화가 어디에 노출되는지 확인하고 감시 범위와 제외 범위를 명시한다.
- 같은 대화가 전체 목록과 채널 목록에 동시에 보이더라도 한 번만 처리한다. 필터는 관찰 범위이며 대화의 고유 식별자가 아니다.
- 감시용 탭과 직원의 응대 화면을 구분한다. 수신함 진입 시 자동 선택된 대화의 읽음 처리도 확인한다. 자동 클릭을 하지 않는 것만으로 미읽음 보존이 보장되지는 않는다.

### 계정·대화 모델

아래 필드는 새 계약의 제안이며, 기존 API가 이미 지원한다는 의미가 아니다.

| 필드 | 의미 |
| --- | --- |
| `source` | 감지 출처 `meta_business_suite`. `channel`과 분리 |
| `channel` | `instagram` 또는 `whatsapp` |
| `account_key` | 고객사와 업무 자산·채널 계정을 연결한 내부 키. 표시 이름이나 탭 ID로 만들지 않음 |
| `scope` | 관찰 중인 채널/필터 범위. 대화 키와 분리 |
| `thread_key`, `identity_quality` | 목록 DOM에서 검증한 대화 ID/링크 기반 키와 식별 신뢰도. 없으면 제한적인 임시 식별임을 표시 |
| `display_name`, `preview` | 화면에 보이는 발신자와 최소 미리보기 |
| `direction`, `unread` | `inbound/outbound/unknown`, 읽음 판별 불가는 `null`. 모르는 것을 수신/0으로 변환하지 않음 |
| `observed_at`, `coverage`, `parser_status` | 감지 시각, 렌더링된 범위, 파싱 상태. 메시지 수신 시각·전체 수신함 개수와 구분 |
| `snapshot_id`, `observer_id`, `sequence` | 재전송 중복 처리와 관찰자별 순서 판정을 위한 값. Meta 메시지 ID가 아님 |

논리 대화 키는 `(account_key, channel, thread_key)`를 기준으로 하고, 감지 출처·파서 버전별 기준 상태는 별도 관리한다. URL의 `asset_id` 같은 값을 발견해도 그것이 Page ID인지 Instagram 계정 ID인지 확인하기 전에는 동등하게 취급하지 않는다. 목록에서 계정을 확인할 수 없으면 명시적으로 등록한 업무 자산과 대조하며, 자산 전환이나 불일치가 발생하면 전송을 멈추고 상태를 보고한다. 잘못된 고객사 Slack 채널로 추정 전송하지 않는다.

안정적인 대화 키를 얻지 못하면 동명이인을 완전히 구분할 수 없다. 이름만 같다고 병합하지 않으며, 모호한 행은 ‘식별 불확실’ 상태로 처리하고 운영 한계로 기록한다.

### 확장 프로그램

- 대상 도메인과 필요한 기능에만 권한을 제한한다.
- 새 DOM 파서는 기존 Instagram 파서와 분리한다. 실제로 확인한 Business Suite 도메인/수신함 경로에서만 실행하며, `*.facebook.com` 전체에 무조건 주입하지 않는다.
- 첫 실행 시 현재 목록을 기준 상태로 저장한다. 기존 대화를 모두 신규로 보내지 않는다.
- 재연결 시 이전 기준과 비교하되, 차이를 확실히 분류할 수 없으면 ‘재연결 후 변경 감지’로 구분한다.
- 짧은 지연을 두어 한 번의 화면 갱신에서 반복 발생하는 DOM 이벤트를 합친다.
- 읽지 않음 여부만 보지 않고, 미리보기와 목록 상태 변화도 함께 판단한다.
- 발신 메시지나 단순 정렬·레이아웃 변경을 가능한 범위에서 제외한다. 판별이 불확실하면 수신 확정으로 표시하지 않는다.
- 브라우저 확장 프로그램 서비스 워커의 중단·재시작을 전제로 상태와 대기열을 영속 저장한다.
- 서비스 워커가 저장 완료를 응답하기 전까지 content script는 전달 완료로 간주하지 않는다. 대기열은 마지막 스냅샷 한 개로 덮어쓰지 않고, 감지한 변경 순서를 보존한다. 서버의 영속 접수 확인 후 제거하며 용량 한도 초과는 조용히 버리지 않고 경고한다.
- 재시도는 서비스 워커의 메모리 타이머에만 의존하지 않고 `chrome.alarms` 등으로 깨워 복구한다. 이에 필요한 권한은 구현 시 추가한다. 서비스 워커 중단과 영속 상태 필요성은 [Chrome 공식 문서](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)에 근거한다.

### 기존 로컬 서버 확장

- 같은 Mac에서 실행하는 기본안은 기존 `http://127.0.0.1:8787` 경로와 ingest 토큰 인증을 재사용한다. 단, 현재 서버의 기본 바인딩은 `0.0.0.0`이므로 loopback 전용이라는 보장은 없다. 구현 시 서비스 접근 범위를 확인해 바인딩/접근 제어를 명시한다. 다른 기기·외부 서버를 통하면 HTTPS를 적용한다.
- 기존 `/api/ingest/instagram`에 WhatsApp 데이터를 억지로 넣지 않고 `/api/ingest/meta`를 추가한다. 클라이언트 인증, 요청 크기 제한, 속도 제한 및 등록된 계정 연결 검증을 적용한다.
- 이벤트를 영속 저장한 뒤 접수 성공을 응답한다.
- `snapshot_id` 접수 이력과 대화 상태/알림 생성을 같은 트랜잭션으로 저장한다. 서버가 저장 후 응답하지 못해 재요청돼도 알림을 다시 만들지 않는다. 같은 관찰자의 지연된 스냅샷이 최신 상태를 덮어쓰지 않도록 순서를 검사한다.
- 계정·관찰 범위별로 활성 감지기 하나를 지정하거나 서버에서 조정한다. 여러 탭이 서로 다른 시점의 상태를 번갈아 올려 신규 변화를 만드는 일을 막는다.
- Slack 전송 성공과 서버 접수를 별도 상태로 관리한다.
- 서버 접수 실패와 확실한 Slack 미전달·일시 제한에는 재시도한다. Slack 도착 여부가 불확실한 타임아웃은 기존 `unconfirmed` 정책을 유지하고 운영 확인 대상으로 남긴다. 모든 실패를 자동 재전송하면 중복 게시될 수 있다.
- Slack 인증 오류나 채널 접근 오류는 무한 재시도하지 않고 운영 오류로 분류한다.
- 기존 Slack Bot token과 `chat.postMessage` 전송을 유지한다. 토큰은 서버 환경에만 두며 확장 프로그램에는 ingest 토큰만 둔다. 새 Incoming Webhook이나 클라우드 중계 서버는 이번 전환의 필수 요소가 아니다.
- 고객이 입력한 미리보기를 Slack 서식으로 그대로 실행하지 않도록 이스케이프하거나 plain_text로 처리한다. 의도하지 않은 멘션을 방지한다.

## 5. Slack으로 전달할 정보

- 채널 구분: Instagram 또는 WhatsApp
- 발신자: 목록에 실제 보이는 이름/아이디. 정확한 아이디가 없으면 표시 이름으로 대체
- 미리보기: 화면에 표시된 범위에서 최대 80~120자
- 감지 시각: 실제 수신 시각과 구별하여 표시
- 이동 링크: 검증된 채널 수신함 링크. 개별 대화 링크는 안정적으로 확보되는 경우에만 사용
- 상태: 신규 감지 또는 재연결 후 변경 감지 등

기본 문구는 ‘Instagram 대화 변경 2개 / WhatsApp 대화 변경 1개’처럼 관찰된 대화 수를 사용한다. 수신 방향이 확인된 경우에만 새 문의로 표현한다. ‘현재 관찰 목록에서 안 읽은 대화 N개’는 판별 가능한 범위에서만 표시하며 전체 미확인 메시지 수로 부르지 않는다. 동일 고객의 연속 메시지는 미리보기 하나로 합쳐질 수 있다. 기존 `core.render()`의 채널별 건수 계산·폴더 표기는 이에 맞춰 수정해야 한다.

전화번호는 기본 마스킹한다. 사진·음성·첨부파일은 다운로드하지 않는다. 목록에 유형이 표시되는 경우 그 유형만 전달한다. 이름과 미리보기도 개인정보가 될 수 있으므로 최소한의 인원만 접근 가능한 채널을 사용한다.

## 6. 누락과 중복에 대한 설계

### 감지와 전달을 구분

1. Meta에 도착했지만 페이지에 표시되지 않음: 확장 프로그램이 복구를 보장할 수 없다.
2. 페이지에는 표시됐지만 감지기가 놓침: DOM 관찰과 제한적인 로컬 상태 재점검으로 줄일 수 있으나 완전 제거는 어렵다.
3. 감지 후 Slack 전송 실패: 영속 대기열과 재시도로 복구한다.

전송 대기열은 3번을 해결하는 장치이지 1번과 2번을 해결하는 장치가 아니다. 로컬 DOM 재점검은 페이지에 이미 있는 상태만 읽으며 새로고침이나 내부 API 호출을 의미하지 않는다.

### 중복 억제

안정적인 메시지 ID가 화면에서 확보된다면 우선 사용한다. 없으면 계정·채널·대화 식별 정보·미리보기·시간 정보 등을 조합한다. 이름이나 미리보기만으로 영구 중복 제거하지 않는다.

‘네’, ‘감사합니다’처럼 동일한 메시지가 반복될 수 있으므로 내용 해시만으로 제거하면 정상 알림을 놓칠 수 있다. 메시지 ID가 없다면 완벽한 중복 제거와 무누락을 동시에 보장할 수 없으며, 본 목적에서는 의심스러운 중복을 일부 허용하는 편이 적절하다.

### 부분 목록과 신규 판정

- 파서 실패·로딩 중·실제 빈 수신함을 구분한다. 파서 실패를 빈 정상 목록으로 접수해 기준 상태나 안 읽음 수를 초기화하지 않는다.
- 가상화된 목록에서 행이 사라졌다고 읽음/삭제로 바꾸지 않는다. 부분 스냅샷은 해당 범위의 관찰 기록이며 전체 대화 목록의 대체본이 아니다.
- 미읽음 증가와 안정적인 미리보기 변화는 감지 근거다. `1분 전 → 2분 전`, 정렬, 담당자, 라벨, 초안, 입력 중 표시만 바뀌는 것은 새 문의가 아니다.
- 직원이 보낸 답장은 수신 알림에서 제외한다. 방향을 판별할 수 없다면 ‘대화 변경’으로 알리고 수신 확정으로 표시하지 않는다. 현재 열어 둔 대화의 수신도 별도 검증한다.
- 처음 화면에 들어온 오래된 대화를 신규 메시지로 단정하지 않는다. 최초 기준 설정뿐 아니라 필터·자산 변경, 재연결에도 기준과 관찰 범위를 함께 관리한다.
- 브라우저 재시작 때 기존 영속 기준을 무조건 지우지 않는다. 다만 파서/계정 변경으로 비교가 불가능하면 다시 기준을 설정하고 그 사이의 감지 공백을 표시한다.

## 7. 감지기 상태 감시

확장 프로그램은 채널별 상태와 생존 신호를 중계 서버로 보낸다. 서버는 신호가 일정 기간 끊기면 Slack에 감지 중단 경고를 보낸다.

구분해야 할 상태:

- 브라우저/확장 프로그램 연결 여부
- 각 채널의 대상 탭 존재 여부
- 로그인 화면 또는 수신함 접근 불가 여부
- 목록 파싱 가능 여부
- 마지막 DOM 변화 시각
- 마지막 이벤트 감지 및 Slack 전달 시각
- 대기 중 이벤트 수와 마지막 오류

현재 `check_instagram_watch()`는 한 번이라도 보고된 Instagram 폴더만 검사한다. Meta 전환 후에는 등록된 감시 대상 목록을 기준으로, 처음부터 열리지 않은 WhatsApp/Instagram 탭도 감지해야 한다. 파싱에 실패하더라도 상태 신호는 별도로 보내 `parser_error`, `login_required`, `asset_mismatch`, `scope_changed` 등을 구분한다. 정확히 판별할 수 없는 상태는 `unknown`으로 보고한다. 기존 5분 무보고 경고를 초기 기준으로 재사용하되 실제 백그라운드 동작에 맞춰 검증한다.

생존 신호가 정상이어도 Meta의 실시간 연결이 정상이라는 뜻은 아니다. 메시지가 없어서 화면이 조용한 상황과 Meta 갱신이 멈춘 상황은 DOM만으로 확실하게 구분하기 어렵다. 실제 테스트 메시지로 종단 간 검증이 필요하다.

중계 서버나 Slack 자체가 중단되면 같은 경로로 장애 경고를 보낼 수 없다. 필요하면 별도 운영 모니터링 경로를 추가한다.

## 8. 정책 및 보안 기준

기존 검토는 Meta의 자동 수집 관련 안내를 근거로 비공식 목록 감지에 정책 위험이 있다고 기록했다. 이번에는 관련 Meta 문서의 본문 재조회가 제한되어 최신 정책을 재검증하지 못했다. 따라서 Business Suite로 옮겼다는 이유로 공식 승인된 연동이나 계정 안전이 보장되는 방식이라고 결론내리지 않는다.

따라서 다음 두 판단은 구분한다.

- 기술적으로 구현 가능: 화면에 나타나는 변화를 확장 프로그램으로 관찰 가능
- 정책상 허용·계정 안전 보장: 현재 확보한 근거로 보장 불가

운영 원칙:

- 대화 자동 열기, 자동 스크롤, 자동 답장, 내부 API 호출 제외
- CAPTCHA나 보안 제한 발생 시 우회하지 않고 중단 및 알림
- 쿠키·세션 토큰 수집 금지
- 최소 권한, ingest 인증, 외부 통신 HTTPS 적용
- 비공개 Slack 채널 및 최소 인원 접근
- 미리보기와 이벤트 저장 기간 제한
- 로그에는 본문 대신 상태·이벤트 식별 정보 위주 저장
- 재시도용 미리보기는 전달 완료 후 정해진 보관 정책에 따라 삭제
- 클리닉 상담 내용의 Slack 이전에 대한 개인정보 처리 기준 검토

## 9. 검증 계획과 통과 조건

### 기능 검증

- Instagram 및 WhatsApp 각각 신규 발신자와 기존 대화에서 메시지 수신
- 동일 문구 반복 수신
- 짧은 시간 연속 메시지 수신
- 본인이 직접 보낸 메시지
- 현재 열어 둔 대화에 수신
- 목록 아래쪽 또는 화면에 보이지 않는 대화에 수신
- 다른 탭 사용 및 장시간 백그라운드 상태
- 같은 표시 이름의 서로 다른 고객, 두 채널에서 같은 이름 사용
- Business Suite 전체 목록과 채널 목록에 같은 대화가 중복 노출
- 다른 직원의 읽음·답장·배정·완료 처리와 수신이 겹치는 상황
- 업무 자산 전환, 필터 변경, 두 탭 간 선택 상태 동기화
- 메시지 요청·스팸·완료 목록에 대한 실제 관찰 범위

### 복구 검증

- 페이지 새로고침과 브라우저 재시작
- 네트워크 끊김 후 복구
- 로그아웃 또는 세션 만료
- 탭 닫힘, 절전 및 복귀
- Slack 일시 오류와 인증 오류
- Meta 화면 구조 변경으로 목록 파싱 실패
- 서버가 저장한 직후 응답 유실, 동일 스냅샷 재전송, 오래된 스냅샷의 지연 도착
- 서비스 워커 강제 종료 후 대기열 복구, 대기열 용량 한도 도달
- 등록만 하고 한 번도 열지 않은 감시 탭, 계정 연결 불일치

### 통과 기준

통제된 테스트에서 실제 보낸 메시지 기록과 Slack 알림을 대조한다. 감지 여부, 지연, 중복, 발신자 오인식, 중단 경고를 기록한다. 메시지별 감지가 불가능하고 대화별 변경만 감지된다면 이를 제품 동작으로 명확히 표시한다.

화면 밖 대화가 일관되게 누락되거나 백그라운드에서 갱신되지 않으면, 페이지 감지 단독으로 ‘놓치지 않기’ 요구를 충족했다고 판정하지 않는다. 공식 API를 사용할 수 없는 동안에는 검증된 OS 알림 보조 경로 또는 수동 확인 절차를 유지해야 한다.

## 10. 권장 추진 순서

1. **Business Suite 화면 검증:** 테스트 대화로 목록 갱신·계정/채널 식별·대화 키·읽음 부작용·필터 범위를 확인한다. 고객 원문·쿠키가 포함된 전체 DOM 덤프를 저장하지 않고 비식별화한 최소 fixture를 만든다.
2. **파서와 계약 구현:** Meta 전용 파서, 공통 스냅샷, 계정 매핑과 DB 마이그레이션을 추가한다. 기존 이름 기반 커서에 새 데이터를 섞지 않는다. 운영 자산을 식별할 수 없으면 Slack 전달보다 진단을 먼저 완료한다.
3. **전달·상태 기능 보완:** 영속 대기열과 접수 중복 방지, 두 채널 상태 감시, 관리 화면·확장 팝업·Slack 문구를 함께 수정한다. 원격 서버 신설보다 기존 서버 재사용을 우선한다.
4. **비교 검증:** 처음에는 Meta 감지 결과만 기록하고 운영 Slack 전송은 끈다. 테스트 채널에서 실제 보낸 기록과 감지/전달 기록을 대조한다. 기존 경로와 병행하더라도 같은 운영 채널에 양쪽이 모두 알림을 보내지 않게 한다.
5. **계정별 전환:** 검증된 계정부터 알림의 활성 출처를 Meta로 전환하고 기존 WhatsApp AX watcher·Instagram 직접 감시를 중지한다. 기존 `pending/retry/unconfirmed` 알림은 출처·수신처를 보존해 별도로 정리한다. 커서 재설정으로 과거 목록 전체를 신규 알림으로 보내지 않는다.
6. **운영 문서 갱신:** 전환 구현이 완료되면 README와 OPERATIONS의 WhatsApp 앱/손쉬운 사용 및 Instagram 3개 창 지침을 실제 구성으로 바꾼다. Meta 목록 감지 자체에는 AX가 필요 없지만 현재 메뉴 막대 앱의 서버 실행·절전 방지 역할은 별개이므로 먼저 확인한다. 전환 실패 시 이전 설정과 감지 기준으로 되돌릴 수 있게 유지한다.

결론: 이번 변경은 **감지 경로의 Business Suite 통합과 기존 알림 서버 확장**으로 진행할 수 있다. 착수 전에 확인할 핵심은 두 채널의 실제 목록 갱신과 안정적인 계정·대화 식별이다. 이 조건이 검증되지 않으면 구현을 완료해도 무누락 수신 시스템이라고 판정할 수 없다.
