# Meta Business Suite 수신함 보조 확장 프로그램 구현 기획서

버전: 1.8 (2026-11-12, Slack 직접 전송, 단일 계정, 상담 탭이 감지를 겸함, 판단은 service worker로 일원화)
이전 버전(v1.7 이하)이나 이름이 다른 사본(spec2, spec copy 등)이 있으면 폐기한다. 이 파일이 유일한 기준이다.
용도: 이 문서만 보고 구현 담당 AI 또는 개발자가 확장 프로그램을 만들 수 있도록 작성한 구현 명세
관련 문서: meta-slack-notification-design.md (검토 배경과 방식 비교)
기존 코드와의 관계: 이 기획서는 기존 chrome-extension/ 과 서버 쪽 작업(instagram_routes 등)에 의존하지 않는 독립 확장 프로그램이다. (2026-11-12 결정) 이 확장 프로그램이 저장소의 메인 제품이고, 기존 코드는 레거시로 제자리에 두며 새 기능을 넣지 않는다. 같은 이름의 설계 문서가 저장소에 서버 경유 결론으로 남아 있다면, 그 문서에 "구현 기획서 v1.2에서 Slack 직접 전송으로 확정"이라고 표시한다.

---

## 0. 구현 담당자가 먼저 알아야 할 것

1. 대상은 Meta Business Suite 수신함 웹페이지(business.facebook.com/latest/inbox/...)에서 동작하는 Chrome Manifest V3 확장 프로그램이다.
2. Meta 공식 API는 쓰지 않는다. 화면(DOM)에 이미 표시된 내용만 사용한다.
3. 4장의 금지 사항은 기능 요구보다 우선한다. 기능을 구현하기 어렵다는 이유로 금지 사항을 어기지 않는다.
4. 3장의 "확인됨" 항목은 2026-11-12에 실제 페이지에서 읽기 전용으로 확인한 사실이다. "미확인" 항목은 추측하지 말고 구현 중 실제 페이지에서 확인한 뒤 진행한다.
5. Meta 화면 구조는 예고 없이 바뀐다. 모든 선택자는 한 파일(selectors.js)에 모으고, 요소를 찾지 못하면 조용히 실패하지 말고 사용자에게 상태를 표시한다.
6. 외부 라이브러리와 빌드 도구 없이 순수 JavaScript로 작성한다. 압축 해제된 확장 프로그램으로 바로 로드할 수 있어야 한다.

## 1. 요구사항과 완료 기준

| 번호 | 요구사항 | 완료 기준 |
|-|-|-|
| R1 | Instagram과 WhatsApp 새 메시지 알림을 Slack으로 받는다 | 수신함 탭이 열려 있는 동안 두 채널 중 어느 쪽에 새 메시지가 와도 화면에 보이는 탭에서는 30초, 가려진 탭에서는 90초 안에 Slack 채널에 알림이 1건 게시된다. 채널 구분이 포함되고, 가능하면 발신자 이름과 미리보기가 포함된다 |
| R2 | 채팅창 말풍선마다 번역, 복사 버튼을 쓸 수 있다 | Instagram, WhatsApp 대화 모두에서 텍스트 말풍선에 마우스를 올리면 두 버튼이 나타나고 클릭하면 동작한다 |
| R3 | 번역 버튼을 누르면 DeepL API로 번역된 한국어를 확인한다 | 클릭 후 해당 말풍선 근처에 한국어 번역문이 표시된다. 원문은 변하지 않는다 |
| R4 | 복사 버튼으로 원문을 복사한다 | 클릭 후 클립보드에 해당 말풍선의 원문 텍스트가 들어간다 |
| R5 | 입력창에 한글을 쓰고 Send 버튼 또는 Enter를 누르면 설정된 언어로 번역되어 전송된다 | 한글이 포함된 입력이 설정 언어로 번역된 뒤 전송되고, 고객에게는 번역문만 도착한다. 한글 원문이 전송되는 경우가 없다 |
| R6 | 채팅창 위 빠른 메시지 버튼으로 저장된 문구를 골라 입력창에 넣고, Send 또는 Enter로 전송한다 | 선택한 문구가 입력창에 들어간다. 자동 전송되지 않는다. 이후 전송 시 R5와 동일하게 동작한다 |
| R7 | 빠른 메시지는 로컬 스토리지에 저장되고 JSON으로 가져오기, 내보내기를 한다 | 설정 화면에서 추가, 수정, 삭제, JSON 파일 내보내기, JSON 파일 가져오기가 된다. 브라우저를 재시작해도 유지된다 |

범위 밖: 여러 계정 동시 운영(계정은 1개만 사용한다), 대화 기록 수집, 자동 답장, 일괄 번역, 첨부 파일 처리, Messenger와 댓글 수신함, 모바일, 스토어 배포.

## 2. 전체 구조

```
[Meta 수신함 탭]
  content script (격리 영역)
    - watcher: 채널 배지와 대화 목록 변화 감지        (R1)
    - bubbles: 말풍선 번역, 복사 버튼                  (R2, R3, R4)
    - composer: 전송 가로채기와 번역, 빠른 메시지 버튼 (R5, R6)
        |  chrome.runtime.sendMessage
        v
[service worker (background)]
    - Slack Incoming Webhook 전송, 재시도 대기열
    - DeepL API 호출
    - 감지 중단 감시 (chrome.alarms)
        |
        v
[options 페이지]
    - Slack Webhook 주소, DeepL 키, 번역 언어, 기능 켬/끔
    - 빠른 메시지 관리, JSON 가져오기/내보내기        (R7)
```

핵심 규칙

- 외부 네트워크 요청(Slack, DeepL)은 service worker만 한다. content script는 fetch를 쓰지 않는다.
- 비밀값(Slack Webhook 주소, DeepL 키)은 content script로 전달하지 않는다. 규약만으로는 강제되지 않으므로 service worker 시작 시 chrome.storage.local.setAccessLevel({accessLevel: 'TRUSTED_CONTEXTS'})를 호출해 content script의 저장소 직접 접근을 막는다. content script는 저장소 API를 쓰지 않고 모든 데이터를 메시지로만 주고받는다.
- content script는 Meta 페이지의 주 실행 영역(main world)에 스크립트를 주입하지 않는다. 격리 영역에서 DOM 이벤트만 사용한다.

### 2-1. 파일 구성

```
extension/
  manifest.json
  background.js          service worker
  content/
    selectors.js         모든 선택자와 화면 구조 판별 함수
    util.js              공통 함수(디바운스, 한글 판별, 토스트)
    watcher.js           R1
    bubbles.js           R2, R3, R4
    composer.js          R5, R6
    content.css          주입 UI 스타일
  options/
    options.html
    options.js
    options.css
  icons/
```

### 2-2. manifest.json 요건

- manifest_version: 3
- permissions: storage, alarms, clipboardWrite
- host_permissions:
  - https://business.facebook.com/*
  - https://hooks.slack.com/*
  - https://api.deepl.com/*
  - https://api-free.deepl.com/*
- content_scripts: matches https://business.facebook.com/latest/*, run_at document_start, all_frames false. 스크립트 안에서 경로가 /latest/inbox 로 시작할 때만 기능을 활성화한다. document_start로 두는 이유는 8장의 가로채기 리스너를 Meta의 리스너보다 먼저 등록하기 위해서다. DOM을 다루는 초기화는 DOMContentLoaded 이후에 한다.
- background.service_worker: background.js
- options_ui: options/options.html (새 탭으로 열기)
- 그 외 권한(tabs, scripting, webRequest, cookies, notifications 등)은 추가하지 않는다.
- chrome.tabs API는 tabs 권한 없이 쓸 수 있는 범위에서만 쓴다: chrome.tabs.onRemoved(탭 닫힘 감지), chrome.tabs.sendMessage. 탭의 주소나 제목이 필요하면 chrome.tabs로 조회하지 않고 content script가 메시지로 알려 온 값을 쓴다.

수신함은 단일 페이지 앱이라 주소가 바뀌어도 페이지가 다시 로드되지 않는다. content script는 한 번 주입된 뒤 주소 변화와 DOM 변화를 스스로 따라가야 한다. matches를 /latest/* 로 넓게 잡은 것은 수신함이 아닌 Business Suite 화면에서 수신함으로 이동해 온 경우에도 동작하게 하기 위해서다.

## 3. 화면 구조 (2026-11-12 확인)

화면 언어는 영어 기준이다. aria-label 문자열은 화면 언어에 따라 달라지므로, 가능하면 구조 기반 선택자(data 속성, role)를 우선하고 문자열 기반 선택자는 보조로만 쓴다.

### 3-1. 주소

| 화면 | 경로 |
|-|-|
| 전체 | /latest/inbox/all |
| Instagram DM | /latest/inbox/instagram_direct |
| WhatsApp | /latest/inbox/wec |
| Messenger | /latest/inbox/messenger |
| Facebook 댓글 | /latest/inbox/facebook |
| Instagram 댓글 | /latest/inbox/instagram |

쿼리 문자열에 selected_item_id(현재 선택한 대화)와 thread_type이 있다. selected_item_id는 대화 구분 키로 쓸 수 있다.

계정 식별값 asset_id (확인됨)

- 수신함 주소의 쿼리 문자열에 asset_id(16자리 숫자)와 business_id가 있다. WhatsApp 탭과 Instagram DM 탭 모두에서 확인했다. mailbox_id도 있으며 asset_id와 같은 값이었다.
- 채널 탭 링크 6개와 왼쪽 메뉴 링크의 href에도 같은 asset_id가 들어 있다. 화면을 이동해도 유지되는 구조다.
- 계정을 전환했을 때 asset_id가 바뀌는지는 확인하지 못했다(U10).

### 3-2. 채널 탭과 배지 (확인됨)

- 채널 탭: `[role="tablist"] a`. href 경로로 채널을 구분한다.
- 배지: 탭 링크 안의 `[role="status"]`. 텍스트가 "1 new", "2 new" 형태다. 뒤에 공백이나 글자가 더 붙는 경우가 있었으므로 맨 앞 숫자만 정규식으로 읽는다. 배지가 없으면 0이다.
- 현재 보고 있는 채널의 배지도 표시되고 증가한다.
- 새로고침 없이 실시간으로 바뀐다. (실제 수신 순간에 WhatsApp 0 → 1, 전체 1 → 2 확인)
- 전체 탭 숫자는 Instagram DM + WhatsApp 등 메시지 채널의 합으로 보이며 댓글은 포함되지 않았다. 따라서 채널별 배지를 각각 읽는다.

### 3-3. 대화 목록 (확인됨, WhatsApp 탭)

- 목록 컨테이너: `[data-pagelet="GenericBizInboxThreadListViewBody"]`
- 각 항목에 채널 아이콘 `img[alt="WhatsApp"]` (Instagram은 alt="Instagram"으로 예상, 미확인)이 있다.
- 항목 요소: 채널 아이콘에서 부모로 6단계 올라간 div. 식별용 속성이 없으므로 "채널 아이콘을 포함하고 `[role="gridcell"]`을 포함하는 가장 가까운 조상"으로 찾는다. 단계 수를 고정하지 않는다.
- 항목의 innerText 줄 순서: 1) 발신자 이름 또는 전화번호, 2) 미리보기, 3) 날짜 단어(Today, Wednesday 등), 4) 시각(오늘이면 "1:59 PM", 이전이면 "Wed" 형태), 5) 라벨(있을 때)
- 내가 보낸 메시지의 미리보기는 "You: "로 시작한다.
- 수신함이 지원하지 않는 유형은 미리보기가 "*Message can't be displayed*"로 시작한다.
- 새 메시지가 오면 해당 대화가 목록 맨 위로 올라온다.
- 항목에 안정적인 대화 ID 속성은 없다. 읽지 않음 표시는 화면상 굵은 글씨지만 최하위 텍스트 요소의 font-weight 검사로는 구분되지 않았다. 읽지 않음 판별을 굵기에 의존하지 않는다.

### 3-4. 대화 영역 (확인됨, Instagram DM과 WhatsApp 모두)

- 메시지 영역: `[role="region"]` 중 aria-label이 "Message list"로 시작하는 요소. 화면 언어 의존을 피하려면 "`[data-message-id]`를 포함하는 `[role="region"]`"으로 찾는다.
- 말풍선: `[data-message-id]` 요소. 값은 "mid.$..." 형태의 메시지 고유 ID다.
- 말풍선 본문: 말풍선 안의 `[dir="auto"]` 요소(텍스트 말풍선마다 1개). innerText가 원문이다.
- 텍스트가 없는 말풍선(사진, 음성, 스티커)은 `[dir="auto"]`가 없거나 비어 있다.

### 3-5. 입력창 (확인됨)

- 입력창: `div[role="textbox"][contenteditable="true"][data-lexical-editor="true"]`. Meta의 Lexical 편집기다. 내부는 p 요소로 구성된다.
- aria-placeholder가 채널에 따라 다르다. (Instagram: "Reply on Instagram…")
- 입력창 주변 버튼(WhatsApp에서 확인): aria-label이 Submit, Share products, Attach a file, Insert saved reply, Post a sticker, Send a voice clip 인 `div[role="button"]`.
- 전송 버튼은 aria-label="Submit"으로 보인다. Instagram 화면에서도 같은지, 입력 내용이 있을 때 모양이 바뀌는지는 미확인이다.
- 입력창 영역은 화면 오른쪽 대화 패널 하단에 있고 폭은 약 400px이다.

### 3-6. 미확인 항목 (구현 중 반드시 확인)

| 번호 | 항목 | 영향 |
|-|-|-|
| U1 | Instagram 대화 목록 항목의 구조와 발신자 표기(아이디인지 표시 이름인지) | R1 |
| U2 | /latest/inbox/all 탭에서 두 채널 대화가 함께 표시되는지 | R1 |
| U3 | 탭이 백그라운드이거나 오래 방치됐을 때 배지와 목록이 계속 갱신되는지 | R1 |
| U4 | 열어 둔 대화에 메시지가 오면 배지가 증가하는지 | R1 |
| U5 | Instagram 화면의 전송 버튼 aria-label | R5 |
| U6 | 합성 붙여넣기 이벤트로 Lexical 입력창 내용을 바꿨을 때 Meta가 정상 인식하는지 | R5, R6 |
| U7 | 번역 후 프로그램으로 전송을 이어서 실행할 수 있는지(전송 버튼 click 또는 합성 Enter) | R5 |
| U8 | service worker에서 DeepL API 호출이 허용되는지 | R3, R5 |
| U9 | 한글 조합 중 Enter를 눌렀을 때의 이벤트 순서(조합 중 keydown 1회만 오는지, 조합 종료 후 keydown이 한 번 더 오는지)와 Meta가 어느 이벤트에서 전송하는지. macOS와 Windows 각각 확인 | R5 |
| U10 | 수신함 안에서 이동하는 동안 주소에서 asset_id가 빠지는 순간이 있는지. 다른 계정 화면에서는 asset_id가 다른 값인지(접근 가능한 다른 계정이 있을 때만 확인) | R1 |
| U12 | 채널 탭 전환이나 화면 갱신 순간 배지 숫자가 잠깐 사라졌다 돌아오는지. 대화 목록이 화면에 보이는 항목만 그리는 방식인지(스크롤 시 항목이 DOM에서 사라지는지). 가려진 탭에서도 목록이 갱신되는지. 목록 항목이 여러 번에 나눠 바뀌는지(이름만 먼저 바뀌고 미리보기는 이전 것인 중간 상태가 있는지). 있다면 가려진 탭의 즉시 판단에서 "같은 항목이 연속 두 번의 관찰에서 동일할 때만 후보"로 보완한다 | R1 |
| U11 | 검색, 필터(Unread, Ad replies, Follow up, Filters)가 켜진 상태를 화면에서 무엇으로 판별할 수 있는지. "읽지 않음으로 표시" 기능이 있는지와 그때 배지가 오르는지 | R1 |

U6~U10은 구현 초기에 가장 먼저 검증한다. U11, U12는 R1 구현 시작 전에 확인한다. 6-1의 안정화 시간(3초, 20초), 감소 대기 시간(3초), 기억 범위(15개)는 이 확인 결과에 맞춰 조정한다. 결과에 따라 7-4(DeepL 호출)와 8-5(입력창 교체, 전송 이어가기)의 대체 경로를 적용한다.

## 4. 금지 사항

1. Meta의 내부 API, GraphQL, 웹소켓을 직접 호출하거나 가로채지 않는다. fetch, XMLHttpRequest, WebSocket을 감싸거나 바꾸지 않는다.
2. 쿠키, 세션 토큰, 로그인 정보를 읽거나 저장하거나 전송하지 않는다.
3. 대화를 자동으로 열거나 클릭하지 않는다. 목록과 대화 영역을 자동으로 스크롤하지 않는다.
4. 페이지를 주기적으로 새로고침하거나 주소를 이동시키지 않는다.
5. 사용자가 누르지 않은 말풍선의 본문을 읽지 않는다. 화면의 말풍선을 일괄로 읽거나 번역하거나 저장하지 않는다.
6. 사용자의 전송 동작 없이 메시지를 보내지 않는다. 확장 프로그램이 전송을 실행하는 경우는 R5에서 사용자가 누른 전송을 번역 후 이어서 완료할 때뿐이다.
7. 대화 내용, 발신자 정보를 Slack과 DeepL 외의 곳으로 보내지 않는다. 분석 도구, 원격 로그를 넣지 않는다.
8. 메시지 본문을 영구 저장하지 않는다. 6-4의 중복 방지 기록과 전송 대기열만 예외이며 보관 기한을 지킨다.
9. 보안 확인 화면, 로그인 화면, 캡차가 나타나면 우회하지 않고 모든 기능을 멈춘다.
10. Meta가 만든 DOM 요소를 삭제하거나 내용을 바꾸지 않는다. 예외는 R5, R6의 입력창 내용 변경뿐이다.

```json
{
  "settings": {
    "slackEnabled": true,
    "slackWebhookUrl": "",
    "assetId": "",
    "accountName": "",
    "slackPreviewMaxLen": 100,
    "slackMaskPhone": true,
    "deeplApiKey": "",
    "bubbleTargetLang": "KO",
    "sendTranslateEnabled": true,
    "sendTargetLang": "EN-US",
    "bubbleButtonsEnabled": true,
    "quickRepliesEnabled": true
  },
  "quickReplies": {
    "version": 1,
    "items": [
      { "id": "uuid", "title": "예약 양식", "text": "예약을 위해 아래 정보를 보내 주세요.", "tags": ["예약"] }
    ]
  },
  "watcherState": {
    "badges": { "instagram_direct": 0, "wec": 0 },
    "badgesKnown": false,
    "ownerTabId": null,
    "lastHeartbeat": 0,
    "everSeen": false,
    "stoppedAlertSent": false,
    "lastAlarmAt": 0
  },
  "threadLangs": {},

  "sentKeys": []
}
```

- threadLangs: 대화별 번역 대상 언어. 키는 selected_item_id, 값은 언어 코드 또는 "OFF". 최대 500개, 초과 시 오래된 것부터 삭제. settings 안에 두지 않는다(설정 응답과 변경 알림마다 통째로 오가지 않게 한다).
- slackQueue: 보류 중이거나 전송 대기 중인 Slack 메시지. 항목에 status("hold" 또는 "ready")와 holdUntil이 있다. 전송 성공 시 삭제. 24시간 지난 항목은 폐기.
- sentKeys: 중복 방지용 키와 시각. 본문이 아니라 해시만 저장. 24시간 후 삭제.
- 번역 결과 캐시는 저장소에 넣지 않고 content script 메모리(Map)에만 둔다.
- content script는 저장소를 직접 읽지 못한다(2장 핵심 규칙). service worker에 GET_PUBLIC_SETTINGS, GET_QUICK_REPLIES 메시지를 보내 비밀값이 제거된 사본을 받는다.
- assetId: 알림 대상 계정의 asset_id. 계정은 1개만 운영한다. 설정 화면의 [현재 수신함을 알림 대상으로 지정] 버튼으로 채운다. 비어 있으면 감지하지 않는다. accountName은 Slack 메시지에 표시할 이름이다.
- watcherState: 배지 기준값(badges, 한 번이라도 저장됐는지는 badgesKnown), 감지 담당 탭, 생존 신호 시각, 중단 경고 상태. service worker만 읽고 쓴다. 목록 기준값은 여기에 두지 않는다(각 탭의 메모리).
- 비밀값은 slackWebhookUrl과 deeplApiKey다. GET_PUBLIC_SETTINGS 응답에서 이 둘을 뺀다.

DeepL 언어 코드 선택지(설정 화면): EN-US, EN-GB, ZH-HANS, ZH-HANT, JA, ES, FR, DE, RU, VI, TH, ID, AR, PT-BR. 실제 지원 목록은 구현 시 DeepL 문서로 확인한다.

## 6. R1: Slack 알림

전달 경로(확정): 확장 프로그램이 Slack Incoming Webhook으로 직접 보낸다. 서버를 경유하지 않는다. 메시지를 저장할 필요가 없고 알림 담당 브라우저가 1대이므로 서버가 맡을 역할이 없다. 계정은 1개만 운영하므로 Webhook 주소도 1개다. 서버가 필요해지는 경우는 14장에 적는다.

### 6-0. 사용 전제

- 알림 전용 탭을 따로 두지 않는다. 상담원이 Instagram 탭 또는 WhatsApp 탭에서 상담하면서 그 탭이 감지도 겸한다. All messages 탭에 머무는 것을 전제로 하지 않는다.
- 따라서 감지는 상담 중의 조작(대화 열기, 완료 처리, 채널 탭 전환, 검색, 필터, 스크롤, 답장)과 섞여도 오알림과 누락이 없어야 한다.
- 알림의 상세 정도는 다음과 같다.

| 상담원이 보고 있는 탭 | Instagram 새 메시지 | WhatsApp 새 메시지 |
|-|-|-|
| Instagram | 채널 + 발신자 + 미리보기 | 채널 + 건수만 |
| WhatsApp | 채널 + 건수만 | 채널 + 발신자 + 미리보기 |
| 수신함 탭 2개(Instagram, WhatsApp 각각) | 채널 + 발신자 + 미리보기 | 채널 + 발신자 + 미리보기 |

- 채널 구분과 "새 메시지가 왔다"는 사실은 어느 경우에도 빠지지 않아야 한다. 이것이 R1의 필수 조건이고, 발신자와 미리보기는 가능할 때만 붙는 부가 정보다.
- 건수만 있는 알림에는 "수신함의 WhatsApp 탭에서 확인하세요"처럼 확인할 위치를 적는다.

### 6-1. 감지 방식

역할 분담 (이 장 전체에 적용)

| 하는 일 | 담당 |
|-|-|
| 화면에서 배지 값 읽기, 목록 후보 찾기 | content script |
| 배지 기준값 보관과 비교, 배지와 목록의 결합, 보류, 중복 방지, Slack 전송 | service worker |

- content script는 "새 메시지인지"를 최종 판단하지 않는다. 본 것을 그대로 보낸다.
- 배지 기준값은 저장소(watcherState.badges)에 있고 service worker만 읽고 쓴다. 감지 담당 탭이 바뀌어도 기준값이 이어지므로 넘어가는 사이의 수신을 놓치지 않는다.
- 목록 기준값(알고 있는 항목)은 탭마다 화면이 다르므로 각 탭의 content script 메모리에 둔다. 저장하지 않는다.

관찰

content script가 MutationObserver로 채널 탭 영역과 대화 목록 영역을 관찰한다. 타이머로 DOM을 주기 조회하는 방식은 보조로만 쓴다(60초마다 1회, 관찰자가 끊겼을 때 대비). Chrome은 5분 넘게 가려진 탭의 타이머를 분당 1회 수준으로 늦추므로, 시간에 민감한 처리를 setTimeout에 의존하지 않는다. 다른 창에 완전히 가려진 창도 같은 제한을 받을 수 있다.

안정화 (오알림 방지의 핵심)

- 다음 직후에는 화면이 나눠서 그려지므로 "안정화 중" 상태로 들어간다: 페이지 로드, 로그인 복귀, 대상 계정 화면으로 복귀, 화면 조건 변경.
- 화면 조건 = 경로(채널 탭) + 검색란 값 + 필터 상태. 검색란은 목록 위 Search 입력란의 값으로 판별한다. 필터(Unread, Ad replies, Follow up, Filters)의 켜짐 여부를 무엇으로 판별할 수 있는지는 미확인이다(U11). 판별할 수 없으면 사용자가 목록 위쪽 필터 영역을 클릭한 것을 화면 조건 변경으로 취급한다.
- 안정화 종료 조건: 배지와 목록에 변화가 없는 상태가 일정 시간 이어진다. 페이지 로드와 로그인 복귀는 20초, 화면 조건 변경은 3초.
- 안정화 중에는 목록 후보를 만들지 않고, 끝날 때의 목록을 "알고 있는 항목"으로 삼는다.
- 배지는 화면 조건 변경(채널 탭 전환, 검색, 필터)의 영향을 받지 않으므로, 화면 조건 변경으로 인한 안정화 중에도 배지 보고는 계속한다. 페이지 로드와 로그인 복귀의 안정화 중에는 배지 보고도 멈추고, 끝난 뒤 첫 보고에 initial 표시를 붙인다.
- 안정화 중에 온 메시지는 목록 신호로는 잡히지 않고 배지 신호(건수 알림)로만 잡힌다.

신호 1: 채널 배지 (모든 채널, 필수)

- 감지 담당 탭의 content script는 instagram_direct, wec 두 탭의 배지 숫자가 바뀌면 디바운스 없이 즉시 BADGE_STATE를 보낸다. 생존 신호(30초)에도 현재 배지 값을 함께 싣는다.
- BADGE_STATE에는 직전 2초 안에 사용자가 대화 목록 영역 또는 대화 상단의 메뉴를 클릭했는지(userActionRecent)를 넣는다. 탭 전체의 클릭으로 잡으면 상담 중에는 항상 참이 되어 의미가 없다. "읽지 않음으로 표시"가 실제로 어느 메뉴에 있는지는 U11에서 확인해 범위를 확정한다.
- service worker는 보고(BADGE_STATE 또는 배지 값이 실린 생존 신호)를 받을 때마다 채널별로 아래 순서를 그대로 따른다. 순서가 바뀌면 알림이 빠진다.
  1. 감소 대기 확정: 감소 대기가 있고 3초 넘게 지났으면, 먼저 기준값을 대기 값으로 내리고 감소 대기를 지운다.
  2. 비교: 받은 값을 (1번을 거친) 기준값과 비교한다.
  3. 받은 값이 기준값보다 크면 "새 메시지" 이벤트를 만들고 기준값을 받은 값으로 올린다. 감소 대기가 남아 있으면 지운다. 증가분이 2 이상이어도 이벤트는 1건으로 하고 건수를 표시한다.
  4. 받은 값이 기준값과 같으면 감소 대기가 남아 있을 때 지운다(숫자가 잠깐 사라졌다 돌아온 것). 이벤트는 없다.
  5. 받은 값이 기준값보다 작으면 기준값을 바로 내리지 않고 감소 대기에 그 값과 시각을 저장한다. 이미 감소 대기가 있으면 값만 바꾸고 시각은 처음 것을 유지한다.
- 예시 1 (읽은 뒤 새 메시지): 기준값 2에서 모두 읽어 0 보고 → 감소 대기(0). 10초 뒤 1 보고 → 1번에서 기준값이 0으로 내려가고, 2~3번에서 0보다 크므로 새 메시지 1건.
- 예시 2 (깜빡임): 기준값 2에서 0 보고 → 감소 대기(0). 1초 뒤 2 보고 → 3초가 안 지났으므로 1번은 건너뛰고, 4번에서 감소 대기를 지움. 알림 없음.
- 예시 3 (깜빡임 중 새 메시지): 기준값 2에서 0 보고, 1초 뒤 3 보고 → 3번에서 새 메시지 1건.
- 생존 신호의 배지 값은 관찰자가 변화를 놓쳤을 때의 안전망이다. 페이지 로드와 로그인 복귀의 안정화(20초) 중에는 생존 신호에 배지 값을 싣지 않는다. 반쯤 그려진 0이 기준값을 내리는 것을 막기 위해서다.
- 채널 탭 전환 순간 배지 숫자가 실제로 잠깐 사라지는지는 미확인이다(U12). 사라지지 않는 것으로 확인되면 감소 대기 시간을 0으로 두어 아래 대가를 없앤다.
- 이 규칙의 대가: 읽음 처리로 숫자가 줄고 3초 안에 다른 메시지가 와서 원래 값으로 돌아오면 배지 신호로는 잡히지 않는다. 그 메시지가 화면에 보이는 채널 것이면 목록 신호로 잡힌다.
- initial 표시가 있는 보고에서 값이 기준값보다 크면 "자리 비운 사이 새 메시지 N건" 알림으로 만든다. 탭이 닫혀 있던 동안의 수신을 놓치지 않기 위해서다.
- 기준값이 한 번도 저장된 적 없으면(설치 직후) 알림 없이 기준값만 저장한다.
- userActionRecent가 참인 증가는 상담원이 "읽지 않음으로 표시"한 것일 수 있다. 배지만으로는 구분할 수 없으므로 알림은 보내되, 발신자 정보가 붙지 않은 건수 알림에는 "수동으로 읽지 않음 표시한 것일 수 있음"을 덧붙인다.

신호 2: 대화 목록 (화면에 보이는 채널, 상세 정보)

- 대상 계정의 수신함 탭이면 감지 담당 여부와 관계없이 모든 탭의 content script가 수행한다.
- 목록이 맨 위까지 올라가 있을 때(목록 스크롤 영역의 scrollTop이 0)만 판단한다. 내려가 있는 동안에는 후보를 만들지 않고, 본 항목을 기억에 추가하기만 한다.
- 내려가 있다가 맨 위로 돌아온 순간은 화면 조건 변경으로 취급해 3초 안정화를 거친다. 그 사이 온 메시지는 이미 건수 알림으로 나갔으므로, 후보로 잡으면 "새 메시지"가 한 번 더 나간다.
- 목록 위쪽 15개 항목의 {채널, 이름, 미리보기, 시각}을 읽는다. 키 = 채널 + 이름 + 미리보기 + 시각. 읽는 범위는 목록 항목의 요약 줄뿐이다.
- 한 번 본 항목의 키는 "알고 있는 항목"에 누적하고 잊지 않는다. 화면에서 사라졌다고 지우지 않는다. 목록을 조금 내렸다 올렸을 때 위쪽 대화를 처음 보는 것으로 오인하지 않기 위해서다. 키는 해시로 메모리에만 두고 최대 500개까지 유지한다(초과 시 오래된 것부터 삭제). 화면 조건 변경으로 안정화에 들어가도 누적된 키는 지우지 않는다.
- 목록이 화면에 보이는 항목만 그리는 방식(가상화)인지는 미확인이다(U12). 그렇다면 스크롤에 따라 항목이 DOM에서 사라지고 나타나므로 위 두 규칙이 더욱 필요하다.
- 목록 변화가 생기면 후보를 찾는다. 탭이 화면에 보이는 상태(document.visibilityState가 visible)면 1.5초 디바운스 후에, 가려진 상태면 디바운스 없이 관찰자 콜백에서 바로 찾는다. 가려진 탭에서는 타이머가 최대 1분 늦어져, 디바운스를 쓰면 후보가 배지 이벤트의 5초 보류가 끝난 뒤에 도착해 같은 메시지로 알림이 두 번 나간다.
- 다음을 모두 만족하는 항목만 후보다.
  - 키가 알고 있는 항목에 없다.
  - 현재 목록에서, 알고 있던 항목 중 가장 위에 있는 것보다 더 위에 있다. 새 메시지는 목록 맨 위로 올라오기 때문이다(3-3). 대화를 완료, 보관 처리해 아래 항목이 위로 밀려 올라온 경우는 이 조건에서 걸러진다.
  - 미리보기가 "You: "로 시작하지 않는다.
  - 미리보기가 "입력 중" 표시(Typing… 등)가 아니다.
  - 시각이 시:분 형태다(오늘 수신).
  - 안정화 중이 아니다.
- 현재 목록의 위쪽 15개 안에 알고 있는 항목이 하나도 없으면 목록이 통째로 바뀐 것이다. 후보를 만들지 않고 화면 조건 변경으로 취급해 안정화로 들어간다.
- 한 번에 후보가 4개 이상이면 같은 방식으로 안정화로 들어간다.
- 후보는 LIST_CANDIDATE로 service worker에 보내고, 현재 목록의 키를 알고 있는 항목에 추가한다.

결합과 보류 (service worker)

- 배지 이벤트는 바로 보내지 않고 최대 5초 보류한다. 그 사이 같은 채널의 LIST_CANDIDATE가 오면(어느 탭에서 온 것이든) 합쳐서 발신자와 미리보기를 붙여 1건으로 보낸다. 5초 안에 없으면 건수만으로 보낸다.
- LIST_CANDIDATE가 먼저 오고 보류 중인 배지 이벤트가 없으면 후보를 5초 보류한다. 그 사이 같은 채널의 배지 이벤트가 오면 합친다. 없으면 목록 정보만으로 알림을 보낸다(열어 둔 대화에 온 메시지처럼 배지가 오르지 않는 경우).
- 보류 항목은 메모리에만 두지 않는다. 만들자마자 slackQueue에 status "hold"와 holdUntil을 넣어 저장한다. service worker는 5초 뒤 setTimeout으로 내보내되, 그 전에 종료될 수 있으므로 시작할 때, 메시지를 받을 때, 알람이 울릴 때마다 holdUntil이 지난 항목을 즉시 내보낸다. chrome.alarms는 최소 간격이 30초라 5초 보류에 쓸 수 없다.
- LIST_CANDIDATE가 왔을 때 붙일 곳은 이 순서로 정한다.
  1. 같은 채널에 보류 중인 배지 이벤트가 있으면 그것과 합친다.
  2. 없고, 같은 채널의 건수 알림을 보낸 지 2분이 안 됐으며 그 알림에 아직 보충 여유가 있으면 보충 메시지로 보낸다. "방금 [WhatsApp] 알림의 상세"라고 표시하고 "새 메시지"라는 제목을 다시 쓰지 않는다.
  3. 둘 다 아니면 후보를 5초 보류했다가 목록 정보만으로 새 알림을 보낸다(위 규칙).
- 건수 알림 1건에 붙는 보충은 그 알림의 건수만큼만 허용한다(1건 알림에는 보충 1개). 건수 알림을 보낸 시각, 채널, 건수, 남은 보충 수를 저장소에 기록해 둔다(본문 없음, 2분 뒤 삭제).
- Instagram 탭과 WhatsApp 탭을 하나씩 열어 둔 경우, 담당이 아닌 탭의 LIST_CANDIDATE 덕분에 두 채널 모두 상세 알림이 된다.

계정 확인

- asset_id는 보고를 만들 때마다 그 시점의 주소에서 직접 읽는다. 주소 변화 감지(12장의 1초 간격 비교)에 의존하지 않는다.
- 주소에 asset_id가 없으면 채널 탭 링크의 href에서 읽는다. 둘 다 없으면 보고하지 않는다. 이 상태가 60초 이상 계속되면 선택자 실패와 같이 취급해 6-5의 경고 대상이 된다. 조용히 감지를 끄지 않는다.
- 운영 계정은 1개다. 설정의 assetId와 일치하는 계정을 보고 있을 때만 보고한다. 다른 계정을 보고 있으면 멈추고 수신함 화면에 "알림 대상 계정이 아닙니다" 표시를 작게 띄운다. 다른 계정 화면의 배지를 새 메시지로 오인하는 것을 막기 위한 장치다.
- 대상 계정 화면으로 돌아오면 로그인 복귀와 같은 안정화(20초)를 거친다.
- assetId가 아직 지정되지 않았으면 보고하지 않고 "설정에서 알림 대상 계정을 지정하세요 [설정 열기]"를 표시한다.

감지 담당 탭

- 대상 계정의 수신함 탭이 여러 개면 그중 하나만 감지 담당이다. 배지 보고(BADGE_STATE)는 담당 탭 것만 처리한다. 목록 후보(LIST_CANDIDATE)는 모든 탭 것을 받는다.
- 후보는 경로가 /latest/inbox 로 시작하고 주소의 asset_id가 설정의 assetId와 같은 탭뿐이다.
- 담당 탭 번호는 watcherState.ownerTabId에 저장한다. service worker는 유휴 시 종료되고 그때 연결(chrome.runtime.connect)도 끊기므로 메모리에만 두면 재시작마다 담당이 바뀐다.
- content script는 연결이 끊기면 다시 연결하고, 연결할 때마다 자기 asset_id와 경로를 알린다. service worker는 저장된 담당 탭이 그대로면 유지한다.
- 담당 탭의 생존 신호가 90초 넘게 없거나, 탭이 닫히거나(chrome.tabs.onRemoved), 그 탭이 다른 계정으로 전환하거나 수신함을 벗어나면 다른 후보 탭에 담당을 넘긴다. 후보가 없으면 담당 없음 상태로 두고 6-5의 중단 감시에 맡긴다. 기준값은 저장소에 있으므로 새 담당의 첫 보고가 그 값과 비교된다.
- 여러 사람이 각자 설치하면 같은 알림이 사람 수만큼 게시된다. 알림 담당 브라우저 1대에서만 slackEnabled를 켠다. 설정 화면에 이 안내를 적는다.

### 6-2. Slack 메시지 형식

Incoming Webhook에 POST. 본문은 JSON, text 필드와 blocks를 함께 보낸다.

```
[WhatsApp] 새 메시지
보낸 사람: Hong G***
내용: 예약 가능한 시간이 궁금합니다...
감지: 14:02
수신함 열기: https://business.facebook.com/latest/inbox/wec
```

- 미리보기는 slackPreviewMaxLen 글자로 자른다.
- 미리보기가 "*Message can't be displayed*"로 시작하면 내용 줄을 "수신함에서 표시되지 않는 유형입니다. WhatsApp Business 앱에서 확인하세요"로 바꾼다.
- slackMaskPhone이 켜져 있고 이름이 숫자로만 된 전화번호면 뒤 4자리만 남기고 가린다.
- 고객이 쓴 문구는 Slack 서식으로 해석되지 않게 한다. blocks에서는 plain_text를 쓰고, text 필드에서는 &, <, > 를 이스케이프한다. @channel 같은 멘션이 동작하면 안 된다.
- accountName이 지정돼 있으면 첫 줄에 함께 표시한다. 예: [계정 이름][WhatsApp] 새 메시지
- 수신함 링크는 채널 경로까지만 넣는다. 개별 대화 링크는 만들지 않는다.

### 6-3. 전송과 재시도 (service worker)

- 알림은 만들어지는 즉시 slackQueue에 저장한다. 보류 중이면 status "hold", 전송 대기면 "ready"다(6-1 결합과 보류).
- 성공(HTTP 200) 시 대기열에서 삭제한다.
- 네트워크 오류, 429, 5xx: 30초, 2분, 10분 뒤 재시도하고, 그 뒤로는 10분 간격으로 24시간(폐기 시점)까지 계속한다. 429는 응답의 Retry-After 값을 우선한다. chrome.alarms를 사용한다. setTimeout에 의존하지 않는다(service worker는 수시로 종료된다).
- 400, 403, 404: 재시도하지 않고 설정 오류로 기록해 options 화면과 확장 아이콘 배지에 표시한다.
- Webhook 주소가 비어 있으면 대기열에 넣지 않고 설정 필요 상태만 표시한다.

### 6-4. 중복 방지

중복 방지는 service worker가 전송 직전에 한다.

- 키: 채널 + 이름 + 미리보기 + 시각의 해시. 배지 전용 알림은 채널 + 배지 값 + 분 단위 시각.
- 같은 키는 10분 동안 다시 보내지 않는다.
- 판단이 애매하면 보낸다. 누락보다 중복이 낫다.

### 6-5. 감지 중단 경고

- 담당 탭의 watcher는 정상 동작 중일 때 30초마다 service worker에 생존 신호를 보낸다. 조건: 수신함 경로이고, asset_id를 읽었고, 채널 탭과 목록 컨테이너를 찾았다. 신호에는 asset_id를 넣는다.
- 감시는 assetId가 지정되어 있고 생존 신호를 한 번이라도 받은(everSeen) 뒤부터 한다.
- 대상 계정이 아닌 화면만 열려 있는 상태가 3분 넘게 이어지면 감지가 멈춘 것이므로 중단 경고 대상이다.
- service worker는 chrome.alarms로 1분마다 마지막 생존 신호 시각을 확인한다. 3분 넘게 없으면 Slack에 "감지가 중단되었습니다. 수신함 탭을 확인하세요" 경고를 1회 보낸다. 신호가 다시 오면 "감지가 재개되었습니다"를 1회 보낸다.
- 로그인 화면 또는 선택자 실패가 60초 이상 계속되면 watcher가 원인을 담아 즉시 알린다.
- 오탐 방지: 설치 후 첫 생존 신호를 받기 전에는 감시하지 않는다. 직전 알람 실행과의 간격이 3분 이상 벌어졌으면(PC 절전 복귀) 이번 회차는 판단하지 않고 한 회차 기다린다.
- 브라우저가 완전히 꺼지면 이 경고도 보낼 수 없다. 이 한계는 설정 화면에 안내 문구로 적는다.

### 6-6. 운영 안내 (설정 화면에 표시)

- 수신함 탭을 닫지 않는다. 상담하던 탭에서 광고 관리 등 수신함 밖으로 이동하면 감지가 멈춘다. 다른 화면은 새 탭에서 연다.
- 두 채널 모두 발신자와 미리보기를 받고 싶으면 Instagram 탭과 WhatsApp 탭을 하나씩 열어 둔다.
- 브라우저의 탭 절전(메모리 절약) 대상에서 business.facebook.com을 제외한다.

## 7. R2~R4: 말풍선 번역, 복사 버튼

### 7-1. 버튼 표시

- 말풍선마다 버튼을 주입하지 않는다. document.body 아래에 떠 있는 도구 모음 1개를 만들어 재사용한다. Meta가 화면을 다시 그릴 때 주입한 요소가 지워지거나 오류를 일으키는 것을 피하기 위해서다.
- 메시지 영역에서 mouseover가 발생하면 event.target.closest('[data-message-id]')로 말풍선을 찾는다. 찾으면 그 말풍선의 위치(getBoundingClientRect) 기준으로 도구 모음을 말풍선 위쪽 모서리에 표시한다.
- 말풍선 안에 내용이 있는 `[dir="auto"]`가 없으면 도구 모음을 표시하지 않는다.
- 마우스가 말풍선과 도구 모음을 모두 벗어나면 300ms 뒤 숨긴다. 스크롤 시에는 즉시 숨긴다.
- 버튼은 [번역] [복사] 2개. 키보드로도 접근 가능하게 button 요소와 aria-label을 쓴다.
- mouseover 처리에서는 말풍선의 위치와 속성만 본다. 본문 텍스트는 버튼을 클릭했을 때만 읽는다.

### 7-2. 복사 (R4)

- 클릭한 말풍선의 `[dir="auto"]` innerText를 navigator.clipboard.writeText로 복사한다.
- 성공하면 버튼 글자를 1.5초간 "복사됨"으로 바꾼다. 실패하면 "복사 실패"를 표시한다.
- 번역문이 표시돼 있어도 복사 대상은 항상 원문이다.

### 7-3. 번역 (R3)

- 클릭 시 원문을 service worker에 보내고, service worker가 DeepL을 호출한다.
- 요청: POST {주소}/v2/translate, 헤더 Authorization: DeepL-Auth-Key {키}, Content-Type: application/json, 본문 {"text": [원문], "target_lang": "KO"}
- 주소: 키가 ":fx"로 끝나면 https://api-free.deepl.com, 아니면 https://api.deepl.com
- 응답의 translations[0].text를 표시한다. detected_source_language도 함께 표시한다(예: "EN → KO").
- 표시 위치: 말풍선 바로 아래에 번역문 상자를 띄운다. 도구 모음과 같은 방식으로 body 아래에 두고 말풍선 위치를 따라가게 하거나, 말풍선 요소의 다음 형제로 삽입한다. 삽입 방식을 택하면 Meta가 다시 그려 지워졌을 때 메시지 ID 기준으로 복원해야 한다. 어느 쪽이든 Meta의 원문 요소는 건드리지 않는다.
- 캐시: Map(메시지 ID → 번역문). 같은 말풍선은 DeepL을 다시 호출하지 않는다. 최대 200개, 페이지를 닫으면 사라진다.
- 번역 버튼을 다시 누르면 번역문을 숨긴다(토글).
- 원문이 이미 한국어로 감지되면 "이미 한국어입니다"를 표시한다.
- 진행 중에는 버튼에 로딩 표시를 하고 중복 클릭을 막는다.

오류 표시

| 상황 | 표시 |
|-|-|
| 키 미설정 | DeepL 키를 설정하세요 (설정 화면 열기 링크) |
| 403 | DeepL 키가 올바르지 않습니다 |
| 456 | DeepL 사용 한도를 초과했습니다 |
| 429, 5xx, 네트워크 | 잠시 후 다시 시도하세요 |

### 7-4. U8 대체 경로

DeepL은 웹페이지에서의 직접 호출을 막는다. 확장 프로그램의 service worker는 host_permissions가 있으면 이 제한을 받지 않는 것이 일반적이지만, 실제 통과 여부를 먼저 확인한다. 막히면 options 화면에 "번역 중계 주소" 설정을 추가하고, 같은 요청 형식을 받아 DeepL로 전달하는 사용자의 중계 서버를 경유하게 한다. 중계 서버 구현은 이 문서의 범위 밖이다.

## 8. R5: 한글 입력을 번역해 전송

가장 깨지기 쉽고 사고 영향이 큰 기능이다. 원칙은 "실패하면 전송하지 않는다"이다.

### 8-1. 동작 흐름

1. 사용자가 입력창에서 Enter를 누르거나 전송 버튼을 클릭한다.
2. 가로채기 조건을 모두 만족하면 원래 전송을 막는다.
3. 입력창을 잠금 상태로 표시하고(테두리 색, "번역 중" 표시) 텍스트를 service worker로 보내 DeepL 번역을 받는다. 전송용 번역은 source_lang을 KO로 지정한다(한영 혼합 문장의 결과 안정).
4. 입력창 내용을 번역문으로 교체한다.
5. 교체가 정확히 됐는지 확인한 뒤 전송을 이어서 실행한다.
6. 전송 후 입력창이 비었는지 확인한다.

### 8-2. 가로채기 조건

아래 6개가 모두 참일 때만 가로챈다. 하나라도 아니면 아무것도 하지 않고 Meta의 원래 동작에 맡긴다.

1. sendTranslateEnabled가 켜져 있다.
2. 현재 대화의 대상 언어가 "끔"이 아니다.
3. 입력창 텍스트에 한글(가-힣, ㄱ-ㅎ, ㅏ-ㅣ)이 1자 이상 있다.
4. 현재 번역 처리 중이 아니다.
5. 확장 프로그램이 이어서 실행한 전송이 아니다(8-5의 통과 표시).
6. 입력창 내용이 직전 번역 결과와 다르다.

보충

- 한글이 없는 입력은 그대로 전송된다. 번역이 끝난 문장에는 보통 한글이 없으므로 이어서 실행한 전송이 다시 가로채이지 않는다.
- 6번: 번역 결과를 그대로 둔 채 다시 전송을 누르면 가로채지 않고 통과시킨다(번역 후에도 고유명사 등으로 한글이 남은 경우를 위한 것이다). 직전 번역 결과 기록은 전송이 끝나거나, 대화가 바뀌거나, 입력창이 비워지면 지운다.

설정 또는 대화별 언어를 아직 받지 못한 상태 (조건 목록과 별개의 규칙)

- 대화를 바꾼 직후에는 그 대화의 대상 언어가 "불러오는 중"이다(8-7). 이때 기본 언어로 번역하면, 대상 언어를 "끔"으로 해 둔 한국인 고객에게 번역문이 갈 수 있다. 아래 규칙을 이 상태에도 똑같이 적용한다.
- 언어 버튼에는 불러오는 동안 "…"을 표시하고, 응답이 500ms 넘게 없으면 다시 요청한다.

- content script는 설정을 메시지로 받으므로 페이지 로드 직후에는 설정이 없을 수 있다. 한 번 받은 설정은 content script 메모리에 남으므로 service worker가 재시작해도 이 상태로 돌아가지 않는다.
- 이 상태에서 한글이 포함된 입력을 전송하려 하면 전송을 막고 "번역 설정을 불러오는 중입니다. 잠시 후 다시 시도하세요"를 표시한 뒤 설정을 다시 요청한다. 한글이 없는 입력은 통과시킨다.

### 8-3. Enter 가로채기

- window에 keydown 리스너를 capture 단계로 등록한다(document가 아니라 window). Meta의 리스너보다 먼저 실행되어야 하므로 document_start 시점에 등록한다.
- 조건: Enter 키이고, Shift, Ctrl, Alt, Meta 키가 눌리지 않았고, event.target이 입력창 안이다. Enter 판별은 event.key === "Enter" 또는 event.code가 "Enter", "NumpadEnter"인 경우로 한다. Windows에서는 조합 중 keydown의 event.key가 "Process"로 오는 경우가 있어 event.key만 보면 놓친다.
- 한글 입력기 조합 중의 Enter(event.isComposing이 true이거나 event.keyCode가 229)는 그대로 통과시키지 않는다. 마지막 글자가 조합 중인 상태에서 Enter를 누르는 것이 한국어 입력의 가장 흔한 경로이고, Meta가 이 이벤트로 전송하면 한글 원문이 그대로 나간다.
  - 이 이벤트는 stopImmediatePropagation으로 Meta에 전달되지 않게 막는다. preventDefault는 호출하지 않는다(입력기가 글자를 확정해야 한다).
  - "전송 대기" 표시를 켜고, compositionend 이벤트 직후 또는 뒤따르는 조합 아님 Enter keydown 중 먼저 오는 쪽에서 가로채기 흐름을 1회 시작한다. 두 이벤트가 모두 와도 "처리 중" 조건으로 한 번만 실행되게 한다.
  - "전송 대기" 표시는 500ms 뒤 자동으로 꺼진다. 입력창이 포커스를 잃거나 대화가 바뀌어도 즉시 끈다. 표시가 남아 있다가 나중의 무관한 조합 종료에서 전송이 시작되면 금지 사항 6번 위반이다.
  - compositionend에서 시작할 때는 한 프레임(8-5와 같은 기준) 기다린 뒤 입력창 텍스트를 읽는다. Lexical이 조합 종료를 내부 상태에 반영하기 전에 읽으면 마지막 글자가 빠진다.
  - 환경에 따라 조합 중 keydown 1회만 오기도 하고, 조합 종료 후 keydown이 한 번 더 오기도 한다. U9로 macOS와 Windows에서 각각 확인한다.
- 가로챌 때 preventDefault와 stopImmediatePropagation을 모두 호출한다.
- 같은 방식으로 keypress, keyup의 Enter도 처리 중에는 막는다.

### 8-4. 전송 버튼 가로채기

- window에 click 리스너를 capture 단계로 등록한다. mousedown, pointerdown도 같은 조건으로 막는다(Meta가 어느 이벤트로 전송하는지 미확인).
- 대상: 입력창과 같은 입력 영역 안에 있고 전송 버튼으로 판별되는 요소. 판별은 selectors.js의 함수 하나로 모은다. 현재 확인된 기준은 aria-label="Submit"인 `[role="button"]`이다. U5 확인 후 Instagram 기준을 추가한다.

### 8-5. 입력창 내용 교체와 전송 이어가기

교체 (U6)

1. 입력창에 포커스를 준다.
2. 입력창 전체를 선택한다(Selection API의 selectNodeContents). Lexical은 선택 변경을 selectionchange 이벤트로 비동기 반영하므로, 선택 후 한 프레임(requestAnimationFrame 1회, 탭이 가려져 있으면 50ms) 기다린다. 기다리지 않으면 교체가 아니라 삽입이 되어 한글과 번역문이 함께 남을 수 있다.
3. 번역문을 text/plain으로 담은 DataTransfer로 paste 이벤트(ClipboardEvent, bubbles와 cancelable true)를 입력창에 발생시킨다.
4. 반영을 기다린 뒤(최대 500ms) 입력창 innerText가 번역문과 같은지 비교한다. 공백과 줄바꿈은 정규화해서 비교한다.
5. 다르면 대체 방법으로 document.execCommand('insertText', false, 번역문)을 시도하고 다시 비교한다.
6. 그래도 다르면 실패로 처리한다(8-6).

입력창의 DOM을 직접 고치는 방법(innerText 대입 등)은 쓰지 않는다. Lexical 내부 상태와 어긋나 한글 원문이 전송될 수 있다.

전송 이어가기 (U7)

1. 통과 표시를 켠다(예: 모듈 변수 bypassUntil = 현재 시각 + 1000ms).
2. 전송 버튼 요소에 click()을 호출한다. 버튼을 찾지 못하면 입력창에 Enter keydown 이벤트를 발생시킨다.
3. 1.5초 안에 입력창이 비워지면 성공이다.
4. 비워지지 않으면 자동 전송이 불가능한 환경으로 보고, 번역문을 입력창에 둔 채 "번역되었습니다. Enter를 한 번 더 눌러 전송하세요" 안내를 띄운다. 이때 번역문에는 한글이 없으므로 다음 Enter는 그대로 전송된다.

U7이 불가능한 것으로 확인되면 4번을 기본 동작으로 삼는다. 이 경우 R5는 "Enter 두 번"으로 충족하며, 설정 화면에 그 사실을 표시한다.

### 8-6. 실패 처리

| 상황 | 처리 |
|-|-|
| DeepL 오류, 시간 초과(10초) | 전송하지 않는다. 한글 원문을 입력창에 그대로 두고 오류를 표시한다 |
| 내용 교체 실패 | 전송하지 않는다. 가능하면 원문을 복원하고 오류를 표시한다 |
| 번역 결과에 한글이 남음(고유명사 등) | 자동으로 전송하지 않는다. 번역문을 입력창에 두고 "번역 결과에 한글이 남아 있습니다. 확인 후 Enter를 한 번 더 누르면 그대로 전송됩니다"를 표시한다. 내용을 고치지 않고 다시 누르면 8-2 조건에 따라 통과된다 |
| 처리 중 대화가 바뀜(selected_item_id 변경) | 즉시 중단한다. 아무것도 전송하지 않는다 |
| 처리 중 사용자가 내용을 수정함 | 중단하고 사용자의 내용을 유지한다 |

"한글 원문 그대로 보내기"가 필요할 때를 위해 입력창 옆 언어 버튼에서 대상 언어를 "끔"으로 바꿀 수 있어야 한다.

### 8-7. 입력창 주변 UI

- 입력 영역 바로 위에 떠 있는 작은 막대를 표시한다: [빠른 메시지] [번역: EN-US ▾]
- body 아래에 두고 입력창 위치를 따라가게 한다. 입력창 높이 변화, 창 크기 변화, 대화 전환 시 위치를 다시 계산한다.
- 언어 버튼을 누르면 언어 목록과 "끔"이 나온다. 선택은 SET_THREAD_LANG 메시지로 service worker에 보내 현재 대화(selected_item_id) 기준으로 저장한다. 대화가 바뀔 때마다 GET_THREAD_LANG으로 그 대화의 값을 받아 온다. 응답이 오기 전까지 그 대화의 대상 언어는 "불러오는 중" 상태다. 기본 언어를 임시로 적용하지 않는다. 응답에는 요청한 대화 번호(threadId)가 함께 오고, 응답을 받은 시점의 현재 대화(selected_item_id)와 같을 때만 적용한다. 다르면 버린다. 대화를 빠르게 연달아 바꾸면 이전 대화의 응답이 늦게 도착해, "끔"인 대화에 앞 대화의 언어가 적용될 수 있기 때문이다. 저장된 값이 없는 대화는 기본값 sendTargetLang을 쓴다.
- 번역 전송이 켜져 있으면 입력창 테두리에 색을 표시해 상태를 알 수 있게 한다. 테두리는 Meta 요소의 스타일을 바꾸지 않고 겹쳐 그리는 요소로 표현한다.
- 전송 직후 마지막 전송의 한글 원문을 막대 아래에 5초간 작게 보여준다(무엇을 보냈는지 확인용). 저장하지 않는다.

## 9. R6: 빠른 메시지 사용

- 8-7의 [빠른 메시지] 버튼을 누르면 목록 창이 입력창 위에 열린다.
- 목록은 제목과 본문 앞부분을 보여준다. 상단 검색창에서 제목, 본문, 태그로 걸러낸다.
- 방향키와 Enter로 선택, Esc로 닫기를 지원한다. 이 창 안의 Enter는 8-3의 가로채기 대상이 아니다(target이 입력창이 아님).
- 항목을 선택하면 본문을 입력창의 현재 커서 위치에 넣는다. 방법은 8-5의 paste 이벤트와 같되 전체 선택은 하지 않는다.
- 넣은 뒤 입력창에 포커스를 돌려준다. 전송하지 않는다.
- 이후 사용자가 Enter 또는 전송 버튼을 누르면 R5 규칙이 그대로 적용된다. 본문이 한글이면 번역되어 전송되고, 한글이 없으면 그대로 전송된다.
- 항목이 없으면 "설정에서 빠른 메시지를 추가하세요"와 설정 열기 링크를 보여준다.

## 10. R7: 빠른 메시지 관리 (options 페이지)

### 10-1. 관리 화면

- 목록, 추가, 수정, 삭제, 순서 변경(위, 아래 버튼).
- 항목 필드: 제목(필수, 50자), 본문(필수, 2000자), 태그(선택, 쉼표 구분).
- 저장은 chrome.storage.local의 quickReplies에 즉시 반영한다. content script는 저장소에 접근하지 못하므로, service worker가 chrome.storage.onChanged를 받아 연결된 수신함 탭에 SETTINGS_CHANGED 메시지(비밀값 제외)를 보내 새로고침 없이 반영한다. content script는 chrome.runtime.connect로 연결을 유지한다.

### 10-2. 내보내기

- 파일 이름: quick-replies-YYYYMMDD.json
- 내용: 5장의 quickReplies 객체 그대로({"version": 1, "items": [...]}). 들여쓰기 2칸, UTF-8.
- Blob과 a 요소의 download 속성으로 저장한다. downloads 권한은 쓰지 않는다.

### 10-3. 가져오기

- input type=file 로 .json 파일을 선택한다.
- 허용 형식: {"version": 1, "items": [...]} 또는 항목 배열.
- 검증: JSON 파싱 가능, 각 항목에 title과 text가 문자열로 존재, 길이 제한 이내, 항목 수 500개 이하.
- 검증 실패 시 기존 데이터를 바꾸지 않고 어느 항목이 왜 틀렸는지 표시한다.
- 검증 통과 시 방식 선택: "합치기"(id가 같으면 덮어쓰고 없으면 추가, id가 없으면 새 id 발급) 또는 "전체 교체".
- 적용 전 "N개 추가, M개 변경" 요약을 보여주고 확인을 받는다.

### 10-4. 그 밖의 설정 항목

- Slack: 사용 여부, 미리보기 길이, 전화번호 가리기
- Slack 연결: Webhook 주소(입력 후 가려서 표시), [테스트 메시지 보내기] 버튼
- 알림 대상 계정: 계정 이름, [현재 수신함을 알림 대상으로 지정] 버튼. 누르면 service worker가 지금 연결돼 있는 수신함 탭들이 HELLO와 HEARTBEAT로 알려 온 asset_id를 쓴다(chrome.tabs로 주소를 조회하지 않는다). 값이 모두 같으면 그것을 저장하고, 서로 다른 값이 있으면 목록을 보여 주고 고르게 한다. 사용자가 asset_id를 직접 찾아 입력할 필요가 없어야 한다. 수신함 탭이 열려 있지 않으면 "수신함을 먼저 여세요"를 표시한다. 지정된 값과 감지 상태를 함께 보여준다.
- DeepL: API 키(가려서 표시), [키 확인] 버튼(/v2/usage 호출로 사용량 표시)
- 번역: 말풍선 버튼 사용 여부, 전송 번역 사용 여부, 기본 대상 언어
- 상태: 마지막 감지 신호 시각, 마지막 Slack 전송 결과, 대기열 건수, 최근 오류
- 안내: 6-6의 운영 안내, 6-5의 한계

## 11. 메시지 규약 (content script ↔ service worker)

| type | 방향 | 내용 | 응답 |
|-|-|-|-|
| GET_PUBLIC_SETTINGS | C → S | 없음 | 비밀값을 뺀 settings |
| BADGE_STATE | C → S | {asset_id, badges: {instagram_direct, wec}, initial, userActionRecent, at} | 없음 |
| LIST_CANDIDATE | C → S | {asset_id, channel, sender, preview, time, at} | 없음 |
| SET_THREAD_LANG | C → S | {threadId, lang} | {ok} |
| GET_THREAD_LANG | C → S | {threadId} | {threadId, lang} (없으면 기본값). content script는 threadId가 현재 대화와 같을 때만 적용 |
| HEARTBEAT | C → S | {asset_id, ok, reason, path, badges} | 없음 |
| HELLO (연결 시) | C → S | {asset_id, path} | {settings(비밀값 제외), role: "owner" 또는 "standby" 또는 "other_account" 또는 "not_configured"} |
| TRANSLATE | C → S | {text, targetLang, purpose: "bubble" 또는 "send"} | {ok, text, detectedLang} 또는 {ok: false, code, message} |
| OPEN_OPTIONS | C → S | 없음 | 없음 |

- 위 표의 메시지는 sender.tab.url이 https://business.facebook.com/ 로 시작할 때만 처리한다.
- options 페이지용 메시지: SEND_TEST_SLACK, CHECK_DEEPL_KEY, GET_STATUS, SET_ASSET_FROM_OPEN_TAB, GET_QUICK_REPLIES. 이 메시지는 sender.id가 자기 확장 프로그램이고 sender.tab이 없으며 sender.url이 자기 확장 프로그램의 options 페이지일 때만 처리한다. content script가 보낸 경우 거부한다(GET_QUICK_REPLIES는 양쪽 허용).
- service worker → content script: SETTINGS_CHANGED(비밀값 제외), WATCHER_ROLE(감지 담당 여부).
- BADGE_STATE는 asset_id가 설정의 assetId와 같고, 보낸 탭이 감지 담당일 때만 처리한다. 그 외에는 버린다.
- LIST_CANDIDATE는 asset_id가 설정의 assetId와 같은 수신함 탭이면 담당 여부와 관계없이 받는다.
- TRANSLATE의 text는 5000자를 넘으면 거부한다.
- service worker는 종료와 재시작을 전제로 한다. 상태는 모두 chrome.storage에 둔다.

## 12. 공통 구현 요건

- 주소 변화 감지: history API를 감싸지 않는다. MutationObserver와 1초 간격의 location.href 비교로 대화 전환과 채널 전환을 감지한다.
- 확장 프로그램을 업데이트하거나 다시 로드하면 기존 탭의 content script는 chrome.runtime 연결이 끊긴다. sendMessage 실패를 잡아 "확장 프로그램이 갱신되었습니다. 페이지를 새로고침하세요" 안내를 1회 표시한다.
- 주입하는 모든 요소에는 고유 접두사(예: mbx-)의 클래스와 id를 쓰고, Meta 스타일과 충돌하지 않게 한다. Shadow DOM 사용을 권장한다.
- z-index는 Meta의 팝업보다 낮게, 본문보다 높게 둔다. Meta의 대화상자가 열리면 주입 UI를 숨긴다.
- 로그는 console.debug로만 남기고 메시지 본문은 로그에 넣지 않는다.
- 화면 언어가 영어가 아닐 때를 대비해 문자열 기반 선택자에는 한국어 대응 값을 추가할 수 있는 배열 구조를 쓴다.
- 각 기능은 설정에서 따로 끌 수 있고, 한 기능의 오류가 다른 기능을 멈추지 않게 try/catch로 분리한다.

## 13. 구현 순서와 검증

### 13-1. 순서

1. 뼈대: manifest, service worker, options 저장, selectors.js
2. 사전 검증: U6, U7, U8, U9, U10을 테스트 대화에서 확인하고 결과를 문서 상단에 기록
3. R7, R6: 빠른 메시지 관리와 입력창 삽입
4. R2, R4, R3: 말풍선 버튼, 복사, 번역
5. R1: Slack 알림, 재시도, 중단 경고. 시작 전에 U11(필터 상태 판별, "읽지 않음으로 표시" 동작)과 U12(배지 깜빡임, 목록 가상화, 가려진 탭 갱신)를 실제 화면에서 확인한다
6. R5: 전송 번역

R5를 마지막에 두는 이유는 3번에서 만든 입력창 삽입과 4번에서 만든 번역 호출을 재사용하고, 오작동 시 고객에게 직접 영향을 주기 때문이다.

### 13-2. 테스트 원칙

- 전송이 일어나는 테스트는 반드시 테스트용 상대 계정과의 대화에서만 한다. 실제 고객 대화에서 전송 테스트를 하지 않는다.
- 테스트 중 실제 고객 대화를 열어 읽음 처리하지 않도록 주의한다.

### 13-3. 테스트 항목

R1

- 같은 문구 반복, 10초 안에 연속 3건
- 내가 답장을 보냈을 때 알림이 오지 않는지
- 채널 탭 전환, 검색, 필터, 목록 스크롤 시 오알림이 없는지

- 로그아웃 상태에서 경고가 오는지

## 14. 알려진 한계와 위험

- 이 확장 프로그램은 Meta가 승인한 연동 방식이 아니다. Meta는 허가 없는 자동 수집을 제한하고 있어 계정 제한 위험이 없다고 보장할 수 없다. 4장은 그 위험을 낮추기 위한 기준이다.
- Slack 알림은 탭이 열려 있고 화면이 갱신되는 동안에만 동작한다. 모든 메시지를 한 건씩 보장하지 않으며, 연속 메시지는 1건으로 합쳐질 수 있다.
- Meta가 화면 구조를 바꾸면 동작이 멈출 수 있다. 특히 R5가 가장 먼저 영향을 받는다.
- 번역 품질은 DeepL에 달려 있다. R5는 확인 단계 없이 전송되므로 오역이 고객에게 그대로 전달될 수 있다.
- 상담 내용이 DeepL로 전송된다. DeepL 유료 API 요금제는 텍스트를 저장하지 않고 학습에 쓰지 않는다고 명시하므로 유료 요금제 사용을 권장한다.
- Slack Webhook 주소와 DeepL 키가 확장 프로그램 저장소에 평문으로 저장된다. 확장 프로그램과 브라우저 프로필을 다른 사람과 공유하지 않는다.
- 상담 내용이 의료 정보에 해당하면 DeepL과 Slack으로의 전송은 처리 위탁, 국외 이전 검토 대상일 수 있다. 무료 DeepL 키(:fx)를 입력하면 설정 화면에서 경고를 표시한다.
- 읽음 처리로 인한 배지 감소와 새 메시지로 인한 증가가 같은 순간에 겹치면 숫자가 그대로여서 배지 신호로는 잡히지 않는다. 이 경우는 목록 신호에 의존한다.
- 상담원이 대화를 "읽지 않음으로 표시"하면 배지가 올라 새 메시지 알림이 나갈 수 있다. 배지만으로는 실제 수신과 구분할 수 없다.
- 채널 탭 전환, 검색, 필터 직후 몇 초(안정화 시간) 동안 온 메시지는 발신자와 미리보기 없이 건수 알림으로만 온다.
- 서버 없이 동작하므로 다음은 지원하지 않는다: 여러 브라우저가 동시에 감지할 때의 중복 제거, 브라우저가 완전히 꺼졌을 때의 중단 경고, 알림 이력 보관. 이 중 하나가 필요해지면 그때 서버 경유를 검토한다.
- 한글 조합 처리(U9)는 운영체제와 입력기에 따라 다르게 동작한다. 지원 환경을 검증한 조합으로 한정하고 설정 화면에 표시한다.
