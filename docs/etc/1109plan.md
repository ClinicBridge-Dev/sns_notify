# WhatsApp 화면 수집 → DB → 한국어 번역 → Slack: MVP 검토안

작성일: 2026-11-09

상태: 구현 전 검토안. 실제 Mac의 접근성 지원·계정·DB·Slack 연결은 시험하지 않았으며, 설치·메시지 발송·계정 변경도 하지 않았다.

## 1. 결론

요청 범위는 MVP로 적절하다. 고객과 상담사의 메시지를 모두 저장하고, 외국어는 원문과 한국어를 보관하며, 고객의 신규 메시지만 지정 Slack 채널로 알린다. Jev 판단·자동답변·WhatsApp 발송은 제외한다.

단, 다음 네 가지를 보완해야 한다.

- 새 알림만 기다리지 말고 접근성 변화 감지와 주기적 재확인을 함께 사용한다.

- 번역보다 원문 저장을 먼저 한다.

- 저장된 메시지와 Slack 발송 대기 항목을 관리해 장애 후 재처리한다.

- 화면에서 관찰할 수 있는 메시지와 전체 모바일 대화 기록을 구분한다.

본 MVP는 ‘화면 기반 준실시간 수집기’다. API처럼 모든 메시지 이벤트를 빠짐없이 전달받는 계약이 없으므로 실기기 시험 전 완전 수집·즉시 전달을 보장할 수 없다.

## 2. 사용자 요구에 대한 판정

### 1) Mac mini에 상담용 WhatsApp 로그인

적절하다. 기존 모바일 계정을 삭제하거나 API로 이전하지 않고 공식 연결된 기기를 사용한다. 1개 계정으로 검증한 뒤 여러 계정으로 확대한다. 다중 계정은 별도 브라우저 프로필 등 독립 세션이 필요하며, Mac 네이티브 앱 하나가 10개 동시 계정을 지원한다고 가정하지 않는다.

연결된 기기에는 모든 과거 메시지와 채팅이 동기화되는 것은 아니다. 공식 도움말은 전체 이력 조회에는 주 기기를 확인하도록 안내한다. [S1]

### 2) 새 알림마다 손쉬운 사용으로 읽기

수정이 필요하다. 알림은 ‘새 메시지가 있을 수 있다’는 신호로만 사용하고, 실제 본문은 대화방에서 읽는다.

알림이 오지 않을 수 있는 시험 사례는 앱을 이미 보고 있는 경우, 음소거 대화방, 알림 미리보기 숨김, 집중 모드, 모바일 상담사의 발신, 연결 복구 후 동기화다. OS 알림 미리보기만 저장하면 긴 메시지와 연속 메시지를 놓치거나 발신자를 잘못 연결할 수 있다.

Apple AXObserver는 앱의 접근성 객체가 내보내는 변화를 구독하는 기능이다. macOS 알림 배너 전체를 범용적으로 구독하는 webhook과 다르며, 대상 객체가 알림을 지원하지 않을 수 있다. [S2]

권장 방식은 지원되는 AX 이벤트로 빠르게 깨우고, 정기적으로 허용된 대화방의 최근 메시지 구간을 겹쳐 읽어 빠진 내용을 보완하는 것이다. ‘안 읽음’만 검사하면 모바일에서 이미 읽은 고객 메시지와 상담사 발신을 놓친다.

주기는 실측으로 정한다. 초기 1계정 시험에서 수초 단위 변화 점검과 더 느린 대화방 순환 점검을 비교하되, UI 부하·계정 수·대화방 수를 확인하지 않고 10계정 전체의 특정 지연을 보장하지 않는다.

### 3) 고객과 상담사 메시지 모두 DB 저장

적절하며 핵심 요구다. 고객사 → WhatsApp 계정 → 대화방 → 메시지의 연결 관계를 명시적으로 둔다.

- 수신: 고객 측 메시지

- 발신: 연결된 상담 계정 측 메시지. 모바일에서 보낸 답변도 수집 대상

- 판별 불명: 내용을 보존하고 검토 대상으로 표시. 임의로 고객으로 처리하지 않음

- 시스템 메시지: 고객/상담사 대화와 구분

이 구분은 화면의 수신/발신 구조와 계정 정보로 하고, GPT·Jev가 문체를 보고 추측하게 하지 않는다. 하나의 상담 계정을 여러 직원이 공유하면 UI만으로 특정 직원 이름까지 식별하지 못할 수 있다. 이 경우 ‘상담 계정 발신’으로 기록한다.

‘모든 내용’은 범위를 나눠야 한다. 이후 동기화되어 화면에 나타나는 텍스트의 양방향 수집을 1차 대상으로 검증한다. 연결 기기에 없는 옛 대화, 관찰 전에 삭제된 메시지, 음성의 의미·이미지 속 글자까지 자동 보존할 수 있다고 약속하지 않는다.

### 4) 한국어가 아니면 원문과 한국어 저장

적절하다. 상담사 발신도 동일하게 적용한다. 원문은 번역 결과로 덮어쓰지 않는다.

- 한국어: 번역 불필요 상태를 저장하고 한국어 필드는 원문을 참조하거나 같은 값을 사용

- 외국어/혼합 언어: 원문과 한국어 번역을 별도 저장

- 언어 불명·이모지·숫자만 있는 메시지: 억지로 의미를 만들지 않고 상태를 기록

- 번역 실패: 원문은 이미 저장되어 있어야 하며 재시도 가능

메시지 ID와 번역 결과의 대응을 유지한다. 짧은 앞뒤 문맥을 제공하더라도 서로 다른 고객사·대화방을 한 문맥으로 섞지 않는다. 숫자·금액·날짜·이름·제품코드·부정 표현의 보존을 평가한다. 번역문은 시스템이 생성한 별도 값이며 고객이 실제 작성한 원문과 구분한다.

### 5) Jev 판단

요청대로 MVP에서 제외한다. 고객/상담사 구분, Slack 채널 선택, 중복 제거에 Jev가 필요하지 않다.

### 6\~7) DB 저장 후 고객 메시지만 Slack으로 원문+한국어 발송

적절하다. 고객사별 Slack workspace/channel ID를 설정하고 코드가 결정하게 한다. 고객의 텍스트에 Slack 멘션 문법이 있어도 자동 전체 호출되지 않도록 plain text/escaping을 적용하고 불필요한 링크 미리보기를 끈다.

- 고객 신규 메시지: 원문+한국어 알림

- 상담사 발신: DB 및 번역 저장만, Slack 고객 알림 없음

- 최초 과거 이력 수집: 저장만, 기존 메시지 일괄 알림 없음

- 운영 시작 이후 연결 장애로 늦게 발견한 고객 메시지: ‘지연 수집’ 표시 후 알림 대상

- 수신/발신 판별 불명: 고객 채널 자동 알림 대신 별도 운영 점검 대상으로 처리

## 3. 권장 처리 순서와 장애 경계

1. 접근성 이벤트 또는 주기 점검으로 대화방을 다시 읽는다.

2. 고객사·계정·대화방·방향을 확인하고 최근 저장 구간과 비교한다.

3. **원문 메시지와 번역 작업을 DB에 먼저 저장한다.** 저장에 실패하면 처리 위치를 전진시키지 않는다.

4. 번역 작업자가 필요한 메시지만 한국어로 번역한다. 수집기는 번역을 기다리지 않고 다음 메시지를 계속 저장한다.

5. 번역 결과를 저장하고, 고객 신규 메시지라면 Slack 발송 대기 항목을 만든다. 가능한 경우 같은 DB 트랜잭션으로 처리한다.

6. 별도 전송 작업자가 대기 항목을 Slack으로 보낸다.

7. 성공 응답을 확인하고 Slack channel과 ts, 전송 시각을 저장한다.

발송 대기함(outbox)은 ‘보낼 알림을 DB 장부에 먼저 적는 방식’이다. 메시지 저장 직후 프로그램이 종료되더라도 재시작하면 아직 보내지 않은 항목을 찾을 수 있다. 작업자는 같은 항목을 동시에 처리하지 않도록 잠금/예약 상태를 사용한다.

### 번역 장애 때의 권장 정책

정상 상태에서는 요구대로 원문+한국어를 함께 보낸다. 다만 번역 서비스가 오래 멈추면 고객 문의 자체가 보이지 않는 문제가 생긴다.

권장 예외는 정해 둔 대기시간을 넘기면 ‘원문 + 번역 대기/실패 표시’를 먼저 보내고, 번역이 끝나면 같은 Slack 메시지에 갱신하거나 연결된 후속 메시지로 보완하는 것이다. 이는 사용자 요구에 대한 운영상 예외 제안이며, 두 언어가 모두 있어야만 알리는 엄격 모드도 선택할 수 있다. 엄격 모드는 번역 장애 시 알림 지연이 길어진다는 비용이 있다.

## 4. 중복과 누락: 반드시 설계할 부분

### 같은 내용의 다른 메시지를 지우면 안 된다

‘대화방 + 본문 + 분 단위 시각’만으로 중복을 제거하면 같은 사람이 연달아 보낸 두 개의 ‘네’를 하나로 합칠 수 있다.

가능하면 안정적인 원본 메시지 ID를 사용한다. 화면에 그런 ID가 없다면 최근 메시지의 순서·방향·시각·내용·앞뒤 문맥을 함께 비교하는 방식이 필요하다. 일시적인 AX UI 객체 식별자는 영구 메시지 ID로 취급하지 않는다. 불명확한 관찰은 버리지 않고 검토할 수 있게 남긴다.

### Slack의 완전한 1회 전송을 쉽게 보장하지 않는다

DB outbox의 고유 키는 내부의 중복 작업 생성을 줄인다. 그러나 Slack이 메시지를 받았는데 응답이 끊기면, 앱은 성공 여부를 모를 수 있다. 이런 상태를 ‘미확인’으로 분리하고 대조·운영자 확인 경로를 둔다. 무조건 재전송하면 중복 알림이 생길 수 있다.

확실한 실패는 재시도하고, 성공은 ts를 저장한다. 성공 여부가 불분명한 경우의 처리 정책까지 있어야 한다. DB와 외부 Slack 사이의 분산 트랜잭션 없이 ‘절대 중복 없음’을 약속하지 않는다.

### 과거 수집과 신규 알림을 분리한다

최초 시작은 기준 상태를 확보하는 단계다. 기존에 보이는 이력을 저장한다고 고객 신규 알림을 모두 보내면 안 된다. 각 메시지에 초기 이력/운영 중 신규/장애 후 보완 같은 수집 모드를 기록한다. 표시된 시각이 불완전하면 신규 여부를 단정하지 않고 보류 상태를 둔다.

## 5. 최소 DB 구조 제안

아래는 구현 계약의 시작점이며 특정 DB 제품은 아직 고정하지 않는다.

### clients

고객사 ID, 표시 이름, Slack workspace/channel ID, 활성 여부.

### accounts

WhatsApp 계정 ID, 고객사 ID, 수집 방식(native/web), 세션 식별값, 마지막 정상 수집 시각, 연결 상태.

### conversations

대화방 ID, 고객사/계정 ID, 원본 대화 식별값(있는 경우), 표시 이름, 참여자 정보(확인 가능한 범위), 동기화 위치·기준 상태.

이름만으로 대화방을 식별하지 않는다. 동일 이름·이름 변경·동일 고객의 여러 고객사 문의를 구분한다.

### messages

내부 메시지 ID, 고객사/계정/대화방 ID, 원본 메시지 ID(있을 때), direction(inbound/outbound/unknown/system), 원문, 메시지 종류, 발신자 정보, 원본 표시 시각, 추정 가능한 전송 시각, 최초 관찰 시각, 시간 정밀도, 수집 모드, 식별 신뢰 상태.

한국어 텍스트, 언어, 번역 상태, 번역 모델/버전, 번역 시각을 같은 테이블 또는 별도 translations 테이블에 둔다. 메시지 수정 감지가 필요하면 원문 버전을 별도로 보존한다.

### jobs / slack\_outbox

번역/Slack 작업 종류, message_id, 상태, 시도 횟수, 다음 시도 시각, 오류, Slack workspace/channel/ts, 고유 중복방지 키.

상태 예시는 대기·처리 중·완료·재시도·미확인·최종 실패다. 고객사별 조회·발송 권한과 데이터 범위를 저장소/프로그램에서 강제한다.

단일 Mac의 작은 시험은 SQLite 같은 로컬 영속 DB로 시작할 수 있다. 중앙 CRM·다중 수집기로 확장할 경우 PostgreSQL 등을 고려한다. 원격 DB만 쓸 때는 네트워크 장애 동안 원문을 보관할 로컬 영속 대기열이 필요하다. 메모리 큐만으로는 재시작 복구가 되지 않는다.

## 6. Slack 전달 방식

MVP에서도 전용 Slack Bot + chat.postMessage를 우선 추천한다. 목적 채널에 필요한 권한으로 참여시키고 개인 사용자의 브라우저 로그인 세션을 상시 프로그램의 인증으로 재사용하지 않는다.

공식 API는 발송 응답으로 channel과 ts를 돌려준다. Incoming Webhook은 더 간단하지만 발송 응답에서 ts를 바로 돌려주지 않아 번역 보완·상태 추적 시 추가 처리가 필요하다. [S3, S4]

Slack 알림에 포함할 항목:

- 고객사와 대화방/고객 표시명

- 실제 메시지 시각과 필요시 지연 수집 표시

- 원문

- 한국어 번역 또는 번역 대기 상태

- 내부 메시지 식별자나 권한 있는 상세 화면 링크

원문이 한국어면 같은 문장을 두 번 보여주지 않아도 된다. DB에서는 한국어 처리 상태를 유지한다. 처음에는 고객 메시지 1건당 알림 1건으로 동작을 검증하고, 묶음·스레드는 이후 조정한다.

Slack은 채널당 대체로 초당 1개 발송 한도가 있으며 429 응답에는 Retry-After를 따른다. 폭주 시 채널별 대기열로 순차 전송한다. [S3, S5] 긴 원문+번역은 분할·파일·상세 링크로 보존하고 잘린 것을 전체 내용이라고 표시하지 않는다. 메타데이터에는 기밀 본문이나 인증정보를 넣지 않는다.

## 7. 권장 MVP 경계

포함 권장:

- WhatsApp 1계정·허용된 1:1 대화방부터 시험

- 고객·상담 계정의 텍스트와 캡션 저장

- 원문/한국어 번역 및 상태 저장

- 고객 신규 메시지만 Slack 알림

- 중복 방지, 재시작 복구, 수집 상태·실패 알림

- 처음부터 고객사/계정/대화방을 분리하는 데이터 구조

추가 범위로 명확히 해야 할 것:

- 모든 이미지·파일 바이너리 다운로드와 보관

- 이미지 OCR, 음성 전사·번역, 영상 내용 분석

- 그룹 대화의 개별 참여자·상담사 판별

- 전체 모바일 과거 이력 복원

- 수정·삭제·사라지는 메시지의 완전한 변경 이력

첫 버전에서 위 기능을 제외한다면 첨부/음성/스티커 수신 자체는 표시하고, 본문을 처리하지 않았음을 남겨야 한다. 사용자의 ‘전부다’가 파일·음성 내용까지 포함한다면 이 기능은 별도 구현 항목으로 포함해야 하며, 텍스트만 저장하고 전체 수집 완료라고 보고하면 안 된다.

제외 확정: Jev 판단, 자동 답변, WhatsApp 발송, Slack 답글을 WhatsApp으로 전송하는 역방향 기능.

## 8. 개발 전 가장 먼저 할 기술 검증

화면 수집 가능성을 확인하기 전에 DB·번역·Slack 전체를 크게 만들지 않는다. WhatsApp 실제 Mac 앱 또는 선택한 Web 세션 한 개에서 아래를 검증한다.

1. 긴 메시지·줄바꿈·연속 메시지의 본문을 빠짐없이 읽는가?

2. 고객 수신과 모바일 상담사 발신을 구별하는가?

3. 앱이 앞/뒤에 있을 때, 음소거 대화방, 알림 꺼짐에서도 재확인으로 잡히는가?

4. 읽지 않은 수치가 0이어도 새 상담사 발신을 수집하는가?

5. 동일한 ‘네’를 같은 분에 두 번 보낸 경우 각각 보존하는가?

6. 인용된 옛 메시지를 신규 메시지로 잘못 중복 저장하지 않는가?

7. 같은 표시 이름의 대화방과 이름 변경을 구분하는가?

8. 원문 저장 직후 종료·재부팅하면 번역과 Slack 작업을 이어가는가?

9. 번역 실패·Slack 429·Slack 응답 타임아웃을 구분해서 복구하는가?

10. 최초 과거 수집은 Slack 알림 없이 진행되고, 운영 중 놓친 고객 메시지는 지연 알림으로 복구되는가?

11. 한 고객사의 메시지가 다른 고객사 채널로 전달되지 않는가?

12. 연결 끊김·잠금·로그아웃을 수집 성공으로 오인하지 않고 운영 알림을 내는가?

예를 들어 정상 연결 상태에서 고객 메시지부터 Slack까지 30초 이내를 초기 측정 목표로 둘 수 있다. 이는 보장 수치가 아니다. 이벤트 경로와 주기 점검 경로의 지연을 따로 측정하고, API/네트워크 장애 시간은 별도 상태로 보여 준다. 1계정 시험을 통과한 다음 10계정·예상 피크 문의량으로 다시 부하 시험한다.

통제된 시험에서 원본 대화와 DB를 대조해 누락·중복·방향 오분류·잘못된 Slack 채널 발송을 확인한다. 오류가 0건 관측됐다고 미래의 완전 무오류를 보장하지는 않는다.

## 9. 보안·운영 최소 조건

- 허용된 고객사/대화방만 수집하고 연결된 기기 등록 권한을 확보한다.

- 손쉬운 사용·화면 기록 권한은 필요한 구성요소에만 준다. 화면을 여는 작업은 읽음 표시 등에 영향을 줄 수 있다.

- Mac 잠금·화면 꺼짐·절전·재부팅 시 수집기가 실제로 작동하는지 구분해 시험한다. 다른 제품의 Locked use 기능이 자체 수집기에 적용된다고 가정하지 않는다.

- 화면 읽기 자동화의 정책상 허용 여부는 API 심사와 별개로 확인한다. 보호된 DB·비공개 프로토콜을 역분석하는 방식으로 대체하지 않는다.

- 원문을 번역 API와 Slack으로 전송하므로 고객사의 위탁·보관·공유 범위를 확인한다. 채널 참여자와 보존 기간을 제한한다.

- API 키는 Keychain 등 보안 저장소로 관리하고 로그에 남기지 않는다.

- 고객 메시지는 데이터로 취급한다. 번역 입력 속 지시가 시스템 설정·수신 채널·권한을 바꾸지 못하게 한다.

- 최소 운영 화면에는 마지막 수집 시각, 연결 상태, 미번역 건수, Slack 대기/실패/미확인 건수, 미수집 가능 구간을 표시한다.

## 10. 최종 권고

이 MVP에서 가장 어려운 부분은 GPT 번역이나 Slack 연결이 아니라 **화면에서 고객·상담사 메시지를 누락 없이 구분해 반복 수집하는 것**이다.

먼저 한 계정의 수집 PoC로 이 부분을 검증하고, 원문 선저장 → 비동기 번역 → 고객 메시지 발송 대기함 → Slack 전송 순으로 구현한다. 수집 계약과 데이터 구조를 먼저 확정하면 이후 Meta 승인 시 수집기만 공식 API 어댑터로 교체할 여지를 남길 수 있다. 현재 구현은 API 승인에 의존하지 않는다.
